\section{Обоснование разработки собственного решения}\label{sec:own-solution}

В предыдущей главе проведён анализ существующих систем управления идентификацией
и установлено, что ни одна из них не удовлетворяет
требованиям~2 (расширяемость процесса ротации)
и~3 (использование ротации как механизма экстренного отзыва).
Keycloak обеспечивает частичную расширяемость через плагины,
однако только постфактум~--- встроить логику \emph{до} ротации невозможно.
Zitadel предлагает автоматическую ротацию,
но не позволяет координировать процесс с внешними системами.
Ory Hydra не предоставляет ни автоматической ротации, ни механизмов уведомления.

Вместе с тем экосистема открытых стандартов~---
JWT~\cite{RFC7519}, JWK~\cite{RFC7517},
OIDC~\cite{OpenIDConnect}, Token Exchange~\cite{RFC8693}~---
предоставляет необходимый фундамент для построения собственного решения.
Проектируемая система должна реализовать следующие функциональные возможности:

\begin{enumerate}
  \item Централизованный выпуск JWT-токенов с контролем содержимого claims.
  \item Автоматическую бесшовную ротацию RSA-ключей подписи по расписанию
    с возможностью ручного запуска.
  \item Доставку токенов и публичных ключей до микросервисов
    без создания единой точки отказа.
  \item Межконтурное взаимодействие через механизм Token Exchange.
  \item Управление конфигурацией клиентов и политик через IaC.
  \item Наблюдаемость: метрики, алерты, журнал событий.
\end{enumerate}

Ключевым архитектурным изменением по сравнению с текущей системой
является переход от модели, в которой каждый микросервис одновременно
выступает PDP и PEP~\cite{AWSPDP},
к модели с централизованным эмитентом и распределённой верификацией:
единственный сервис выпускает токены и владеет закрытым ключом,
а все микросервисы верифицируют токены с помощью открытого ключа,
не имея возможности выпускать новые.

\section{Доменная модель системы авторизации}\label{sec:domain-model}

Проектируемая система оперирует шестью основными сущностями,
связи между которыми представлены на \firef{fig:er-diagram}.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/ch2_er_diagram}
  \caption{ER-диаграмма доменной модели системы авторизации}
  \label{fig:er-diagram}
\end{figure}

\textbf{Клиент авторизации} (\texttt{auth\_clients})~---
микросервис или внешняя система, зарегистрированные в системе авторизации.
Каждый клиент имеет уникальный идентификатор (\texttt{client\_id}),
тип (\texttt{client\_type}: Kubernetes, Octopus, Custom)
и набор ограничений: разрешение на произвольные claims (\texttt{allow\_custom\_claims})
и обязательные claims (\texttt{enforced\_claims}),
которые должны присутствовать в каждом выпущенном токене.

\textbf{Политика токенов} (\texttt{token\_policies})~---
именованный набор параметров выпуска токена, привязанный к клиенту.
Определяет время жизни токена (\texttt{time\_to\_live\_in\_seconds}),
список разрешений (\texttt{permissions}),
признак полного доступа (\texttt{full\_access})
и версию политики (\texttt{version}),
позволяющую оператору обнаруживать изменения конфигурации.

\textbf{API-ключ} (\texttt{api\_keys})~---
альтернативный механизм аутентификации для внешних систем,
которые не поддерживают JWT (например, Grafana).
Каждый ключ привязан к клиенту и имеет жизненный цикл
с отслеживанием даты последней ротации.

\textbf{Доверенный эмитент} (\texttt{trusted\_issuers})~---
внешняя система, токенам которой доверяет сервис авторизации.
Содержит способ получения публичных ключей
(\texttt{storage\_type}: OIDC, JWKS, статические ключи),
группы доступа (\texttt{access\_type\_groups})
и параметры валидации.

\textbf{Ротация ключей} (\texttt{rsa\_rotations})~---
запись о текущей или завершённой ротации RSA-ключа.
Хранит текущий шаг выполнения, статус,
источник запуска (расписание или ручной),
а также счётчики ping-пауз,
обеспечивающие устойчивость к инфраструктурным сбоям.

\textbf{Журнал событий} (\texttt{event\_log\_entries})~---
аудиторский след всех значимых действий в системе:
выпуск токенов, изменение конфигурации, ротация ключей.
Используется для доставки событий в SIEM через Outbox-паттерн.

\section{Архитектура системы}\label{sec:architecture}

Система состоит из четырёх компонентов и клиентской библиотеки,
каждый из которых решает определённый набор задач (\firef{fig:architecture}).

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/architecture-overview.drawio}
  \caption{Архитектура системы авторизации}
  \label{fig:architecture}
\end{figure}

\textbf{Микросервис авторизации (Services)}~---
HTTP API, являющийся основной точкой входа для всех запросов.
Реализует следующие функции:
генерация JWT-токенов по политикам (\texttt{POST /token}, \texttt{POST /custom-token});
обмен токенами для межконтурного взаимодействия (\texttt{POST /exchange-token});
синхронизация наборов токенов для оператора (\texttt{POST /token-set/\{clientId\}/sync});
публикация открытых ключей (\texttt{GET /jwks});
CRUD API для управления клиентами (используется Terraform Provider);
выпуск токенов разработчикам через Google OIDC.

\textbf{Фоновый процесс (Worker)}~---
компонент, выполняющий задачи по расписанию:
ротация RSA-ключей,
обработка журнала событий (Outbox-паттерн для доставки в Kafka),
сбор метрик ротации
и автоматическое восстановление зависших ротаций.

\textbf{Kubernetes-оператор}~---
компонент, отвечающий за доставку токенов и публичных ключей
до микросервисов платформы.
Следит за Custom Resource \texttt{AuthJwtConfig}
и каждые 30~секунд выполняет reconcile-цикл,
записывая актуальные данные авторизации в K8s Secret.

\textbf{Terraform Provider и модуль}~---
IaC-инструментарий для управления конфигурацией системы.
Terraform Provider реализует CRUD-операции через API микросервиса авторизации,
а Terraform-модуль является единственным способом
управления клиентами, политиками и доверенными эмитентами.

\textbf{Mindbox.Authentication}~--- клиентская библиотека для .NET-микросервисов.
Проверяет подпись и срок действия JWT на входящих запросах,
читает JWKS из K8s Secret,
предоставляет интерфейсы для чтения токенов (\texttt{ITokenStore})
и синхронного получения токенов (\texttt{IAuthJwtClient}),
а также автоматически подставляет JWT в исходящие HTTP-запросы.
Библиотека обнаруживает ротацию ключей по несовпадению \texttt{kid}
и инвалидирует внутренний кеш.

Для гранулярного контроля доступа используется механизм enforced claims~---
утверждения, которые обязаны присутствовать в токене запрашивающей стороны.
Например, для GitLab CI можно ограничить доступ
конкретной веткой конкретного проекта
через enforced claims \texttt{project\_path} и \texttt{ref}.
Микросервисы аутентифицируются по ServiceAccount-токену Kubernetes,
при этом авторизация выполняется по namespace:
namespace микросервиса должен совпадать с \texttt{client\_id}.

\section{Механизм доставки данных авторизации}\label{sec:delivery}

Централизация выпуска токенов порождает проблему доставки:
каким образом 160~микросервисов получают актуальные токены и публичные ключи,
не превращая микросервис авторизации в единую точку отказа?
Рассмотрены два подхода.

\textbf{Sidecar-агент}~--- дополнительный контейнер,
развёрнутый в каждом поде рядом с микросервисом.
Агент периодически запрашивает данные авторизации
и записывает их в общий том.
Достоинство: агент изолирован и не зависит от других микросервисов.
Недостаток: количество экземпляров агента пропорционально числу подов
(сотни), что создаёт значительную нагрузку на микросервис авторизации
и увеличивает потребление ресурсов кластера.

\textbf{Kubernetes-оператор}~--- единственный компонент на кластер,
который следит за декларативными спецификациями (Custom Resource)
и записывает данные авторизации в K8s Secret (\firef{fig:operator-delivery}).
Достоинство: один экземпляр оператора обслуживает все микросервисы кластера;
микросервисы читают файл из Secret, не выполняя HTTP-запросы.
Недостаток: дополнительный Custom Resource Definition в кластере.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.85\textwidth]{diagrams/img/ch2_operator_delivery}
  \caption{Доставка токенов и JWKS через Kubernetes-оператор}
  \label{fig:operator-delivery}
\end{figure}

Для проектируемой системы выбран подход с оператором,
поскольку он минимизирует нагрузку на микросервис авторизации
и не требует модификации подов микросервисов.
Оператор выполняет reconcile-цикл каждые 30~секунд:
читает спецификацию \texttt{AuthJwtConfig} CR,
запрашивает токены и JWKS у микросервиса авторизации
и записывает результат в K8s Secret (\texttt{auth.json}).
Микросервис читает этот файл через \texttt{Mindbox.Authentication},
которая отслеживает изменения через \texttt{FileSystemWatcher}.

Для токенов, требующих данных из рантайма (например, идентификатор тенанта),
предусмотрен второй режим~--- прямой запрос к микросервису авторизации
через интерфейс \texttt{IAuthJwtClient},
со встроенным in-memory кешем и автоматической инвалидацией при ротации.

Характеристики двух режимов приведены в \taref{tab:token-modes}.

\section{Проектирование процесса ротации ключей}\label{sec:rotation-design}

Процесс ротации состоит из трёх шагов с двумя паузами между ними
(\firef{fig:rotation-sequence}).
Каждый шаг изменяет состояние ключей в хранилище,
а паузы обеспечивают время для распространения обновлений по системе.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/ch2_rotation_sequence}
  \caption{Последовательность ротации RSA-ключей}
  \label{fig:rotation-sequence}
\end{figure}

\textbf{Шаг~1. Создание нового ключа.}
Генерируется новый RSA-ключ (Ключ~B)
и записывается в хранилище как SECONDARY.
PRIMARY (Ключ~A) продолжает использоваться для подписи.
Оба ключа публикуются через JWKS endpoint.

\textbf{Пауза~1. Ожидание доставки JWKS} ($\sim$10~минут).
Оператор должен доставить обновлённый JWKS
(содержащий оба ключа) до всех микросервисов.
Пока микросервисы не знают о Ключе~B,
переключать подпись нельзя~--- новые токены не пройдут проверку.

\textbf{Шаг~2. Swap ключей.}
PRIMARY и SECONDARY меняются местами:
Ключ~B становится PRIMARY, Ключ~A~--- SECONDARY.
С этого момента новые токены подписываются Ключом~B.
Токены, подписанные Ключом~A, остаются валидными~---
микросервисы проверяют подпись обоими ключами.

\textbf{Пауза~2. Ожидание обновления токенов} ($\sim$10~минут).
Токены, подписанные старым ключом, должны выйти из обращения.
Оператор обновляет токены в Secret,
а \texttt{Mindbox.Authentication} обнаруживает несовпадение \texttt{kid}
и не отправляет запрос со старым токеном.

\textbf{Шаг~3. Удаление старого ключа.}
SECONDARY (Ключ~A) удаляется из хранилища.
В системе снова один активный ключ.

\subsection{Ping-механизм и устойчивость к сбоям}\label{subsec:ping}

Паузы между шагами реализованы не через фиксированное ожидание,
а через ping-механизм:
на каждой итерации система выполняет HTTP-запрос к собственному \texttt{/jwks} endpoint.
При успешном ответе счётчик пингов инкрементируется.
Для перехода к следующему шагу необходимо 10~успешных пингов
с интервалом около 1~минуты.
Счётчик хранится в PostgreSQL
(поля \texttt{after\_new\_key\_created\_delay\_count}
и \texttt{before\_old\_key\_deleted\_delay\_count} в таблице \texttt{rsa\_rotations}),
поэтому прогресс не теряется при рестарте пода.

Такой подход обеспечивает устойчивость к инфраструктурным сбоям:
при отказе зоны доступности пинги не проходят
и ротация автоматически приостанавливается до восстановления;
при недоступности хранилища ключей шаг завершается с ошибкой,
но существующие ключи остаются нетронутыми;
фоновая задача \texttt{ResolveStuckRotationsJob}
каждые 5~минут обнаруживает зависшие ротации и перезапускает их.

\subsection{Инварианты ротации}\label{subsec:invariants}

Корректность ротации гарантируется пятью инвариантами:
\begin{enumerate}
  \item Токены всегда подписываются PRIMARY-ключом.
  \item Проверка подписи выполняется по всем активным ключам (PRIMARY + SECONDARY).
  \item Закрытые ключи хранятся только в Vault;
    доступ имеет только микросервис авторизации.
  \item Открытые ключи доступны через \texttt{/jwks} endpoint
    и через оператор (в JWKS-секции K8s Secret).
  \item В любой момент времени активно не более двух ключей.
\end{enumerate}

\subsection{SLO и расписание ротации}\label{subsec:rotation-schedule}

На ротацию установлен SLO~--- 30~минут на полный цикл.
Превышение этого порога вызывает предупреждающий алерт.
Если ключи не ротировались более 8~дней,
срабатывает критический алерт.

Расписание ротации привязано к техническому окну обслуживания (\taref{tab:rotation-schedule}).
Продуктивные контуры ротируются еженедельно,
а тестовые~--- ежедневно для раннего обнаружения проблем.

\section{Межконтурное взаимодействие}\label{sec:exchange}

Каждый контур имеет собственный экземпляр микросервиса авторизации
с отдельными RSA-ключами.
Токен, выпущенный в одном контуре, невалиден в другом~---
подписи различаются.
Это обеспечивает изоляцию: компрометация ключей одного контура
не затрагивает остальные.

Когда микросервису необходимо обратиться к сервису в другом контуре,
используется механизм Token Exchange~\cite{RFC8693} (\firef{fig:exchange-sequence}).

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/ch2_exchange_sequence}
  \caption{Межконтурная авторизация через Token Exchange}
  \label{fig:exchange-sequence}
\end{figure}

Процесс состоит из трёх этапов.
На первом этапе микросервис получает exchange-токен
у микросервиса авторизации своего контура.
Exchange-токен~--- это JWT с коротким временем жизни (5~минут),
пригодный исключительно для обмена.
На втором этапе exchange-токен предъявляется
микросервису авторизации целевого контура,
который проверяет подпись по публичным ключам исходного контура
(доверительное отношение типа ExternalAuthJwt)
и выпускает токен целевого контура.
На третьем этапе полученный токен используется
для авторизованного запроса к микросервису целевого контура.

Exchange реализуется через выделенных exchange-клиентов:
в целевом контуре создаётся клиент,
связанный с исходным клиентом и копирующий его политики.
Микросервис авторизации целевого контура выдаёт токены exchange-клиента
только если запрос пришёл от связанного исходного клиента.

При работе через оператор exchange выполняется автоматически~---
микросервису не нужно знать о механизме обмена.
В K8s Secret записывается готовый токен целевого контура,
и в коде он используется как обычный токен.

\section{Управление конфигурацией через IaC}\label{sec:iac-management}

Конфигурация системы авторизации~---
клиенты, политики, доверенные эмитенты, exchange-правила~---
управляется исключительно через Terraform.
Для этого разработаны два компонента:
Terraform Provider, реализующий CRUD-операции через API микросервиса авторизации,
и Terraform-модуль, содержащий конфигурацию всех клиентов платформы.

Terraform-модуль является единственным источником истины
о конфигурации авторизации.
Изменения проходят стандартный цикл разработки:
ветвление, code review, применение через CI/CD-пайплайн.
Состояние хранится в S3, а раскатка выполняется через Octopus Deploy.

Пример конфигурации клиента:
\begin{verbatim}
"db-workload": {
  allow_custom_claims = false
  token_policies = {
    "nexus": {
      ttl_seconds = 3600
      permissions = [
        "CanReadTenantDatabasesMetadata",
        "CanReadDatabaseFarms"
      ]
    }
  }
  exchange_clients = {
    infra = {
      "nexus-db-workload": {
        expected_contours = ["ru"]
        token_policy_refs = ["nexus"]
      }
    }
  }
}
\end{verbatim}

Такой подход обеспечивает воспроизводимость конфигурации на всех контурах,
полную историю изменений в Git
и возможность рецензирования каждого изменения.

\section{Подбор инструментальных средств}\label{sec:tools}

Выбор инструментальных средств определяется
техническими требованиями из раздела~\ref{sec:requirements},
существующей экспертизой команды и готовностью инфраструктуры.

\textbf{PostgreSQL}~--- основная база данных системы.
Хранит конфигурацию клиентов, политики, доверенных эмитентов,
состояние ротации и журнал событий.
Выбор обусловлен тремя факторами:
в компании накоплена экспертиза по эксплуатации PostgreSQL,
готова инфраструктура развёртывания,
а характер нагрузки (простые SELECT-запросы по первичному ключу)
не требует специализированных решений.

\textbf{HashiCorp Vault}~\cite{HashiCorpVault}~--- хранилище закрытых RSA-ключей.
Доступ к Vault имеет исключительно микросервис авторизации~---
ни один другой микросервис не может прочитать закрытый ключ.
Vault уже используется в платформе для управления секретами,
что позволяет задействовать существующую инфраструктуру и экспертизу.

\textbf{Dragonfly}~--- распределённый кеш, совместимый с протоколом Redis.
Используется для кеширования конфигурации клиентов
по принципу многоуровневого кеша (\firef{fig:cache-layers}):
in-memory кеш как L1, Dragonfly как L2, PostgreSQL как L3.
Выбор Dragonfly обусловлен более высокой производительностью
по сравнению с Redis при многопоточной нагрузке
и полной совместимостью с существующими клиентскими библиотеками.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.8\textwidth]{diagrams/img/ch2_cache_layers}
  \caption{Трёхуровневая схема кеширования}
  \label{fig:cache-layers}
\end{figure}

\textbf{C\#}~--- язык реализации микросервиса авторизации и клиентской библиотеки.
Является стандартом разработки в компании.
Экосистема Microsoft предоставляет развитые библиотеки
для работы с аутентификацией и авторизацией
(\texttt{Microsoft.AspNetCore.Authentication},
\texttt{Microsoft.IdentityModel.Tokens}),
что существенно сокращает объём собственного кода.

\textbf{Go}~--- язык реализации Kubernetes-оператора и Terraform Provider.
Выбор обусловлен наличием Operator SDK и \texttt{client-go}~---
официальных библиотек для разработки операторов и взаимодействия с Kubernetes API,
а также тем, что Terraform Provider SDK доступен исключительно на Go.

\textbf{Kafka}~--- очередь для доставки событий в SIEM.
Микросервис авторизации не пишет в Kafka напрямую~---
используется Outbox-паттерн (\firef{fig:outbox}):
события сохраняются в таблицу \texttt{event\_log\_entries} PostgreSQL
в той же транзакции, что и основное действие,
а фоновая задача \texttt{ProcessEventLogJob}
читает необработанные события и отправляет их в Kafka.
Такой подход гарантирует согласованность~---
событие записывается только при успешном завершении операции.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.85\textwidth]{diagrams/img/ch2_outbox_pattern}
  \caption{Outbox-паттерн доставки событий в Kafka}
  \label{fig:outbox}
\end{figure}

\textbf{Quartz.NET}~--- планировщик фоновых задач.
Используется для выполнения ротации по расписанию,
обработки журнала событий и сбора метрик.
Состояние планировщика хранится в PostgreSQL,
что обеспечивает корректную работу при рестартах пода.

Микросервис авторизации следует типовой архитектуре,
принятой в компании: разделение на слой моделей,
сервисный слой с бизнес-логикой,
Worker для фоновых задач и Migrator для управления схемой базы данных.
Интеграционные тесты используют Testcontainers~---
PostgreSQL, Vault и Dragonfly поднимаются в контейнерах,
что обеспечивает воспроизводимость тестового окружения.

\section{Наблюдаемость}\label{sec:observability}

Для выполнения требования~8 (наблюдаемость)
система предоставляет метрики в формате Prometheus
через библиотеку \texttt{prometheus-net}.
Метрики разделены на четыре группы (\taref{tab:alerts}).

\textbf{Генерация токенов.}
Отслеживаются задержка генерации на 95-м процентиле
и доля неуспешных запросов к каждому endpoint.
Алерт срабатывает при p95 > 30~мс или при доле 5xx > 1\%.

\textbf{Ротация ключей.}
Метрика \texttt{rsa\_last\_completed\_rotation\_age\_hours}
показывает, сколько часов прошло с последней успешной ротации.
Метрика \texttt{rsa\_running\_rotation\_info}
содержит информацию о текущей ротации: шаг, источник запуска, время.

\textbf{Оператор.}
Контролируются наличие reconcile-циклов,
время выполнения reconcile на 95-м процентиле,
статусы полученных токенов и количество рестартов пода.

\textbf{Доверенные эмитенты.}
Отслеживается успешность получения публичных ключей
от каждого доверенного эмитента.

  \centering

  \label{tab:alerts}
  \begin{tabularx}{\textwidth}{X l X}

    \textbf{Алерт} & \textbf{Уровень} & \textbf{Условие} \\

    TokenGenerationLatency & warning &

    RequestFailureThreshold & warning &
      Доля 5xx > 1\% за 5 мин \\
    RsaRotationTakesTooLong & warning &

    OperatorHasNoReconciles & critical &

\section{Выводы по главе}\label{sec:ch2-conclusion}

В данной главе спроектирована архитектура системы авторизации,
состоящей из четырёх компонентов:
микросервиса авторизации (Services и Worker),
Kubernetes-оператора для доставки данных,
Terraform Provider для управления конфигурацией
и клиентской библиотеки Mindbox.Authentication.

Спроектирован трёхшаговый алгоритм бесшовной ротации ключей
с ping-механизмом, обеспечивающим устойчивость к инфраструктурным сбоям.
Определён механизм межконтурного взаимодействия на основе Token Exchange
и система доверительных отношений для аутентификации запросов.

Оценка покрытия технических требований
приведена в \taref{tab:requirements-coverage}.

(многоуровневое кеширование, stateless-компоненты),
однако фактическое подтверждение возможно только
по результатам нагрузочного тестирования,
которое описано в следующей главе.

Следующая глава посвящена реализации спроектированной системы,
интеграционному и нагрузочному тестированию,
а также переводу микросервисов платформы на новую систему авторизации.
