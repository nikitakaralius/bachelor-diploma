\section{Обоснование разработки собственного решения}\label{sec:own-solution}

Анализ, проведённый в предыдущей главе, показал,
что ни одна из рассмотренных систем управления идентификацией
не удовлетворяет сформулированным техническим требованиям в полной мере.
При этом рассмотренные открытые стандарты
предоставляют необходимый фундамент для построения собственного решения.
Проектируемая система должна реализовать следующие функциональные возможности:

\begin{enumerate}
  \item Централизованный выпуск JWT-токенов с контролем содержимого claims.
  \item Аутентификацию потребителей токенов~---
    микросервисов, CI/CD-пайплайнов, шагов деплоя, разработчиков~---
    с разграничением доступных операций.
  \item Автоматическую бесшовную ротацию ключей подписи по расписанию
    с возможностью ручного запуска.
  \item Безопасное межконтурное взаимодействие.
  \item Поддержку внешних систем, не работающих с JWT,
    через альтернативный механизм аутентификации.
  \item Управление конфигурацией клиентов и политик через IaC.
  \item Наблюдаемость: метрики, алерты, журнал событий.
\end{enumerate}

Для реализации перечисленных возможностей
необходимо изменить архитектуру авторизации.
В текущей системе каждый микросервис одновременно
выступает PDP и PEP~\cite{AWSPDP}
и владеет закрытым ключом подписи~---
именно это является корневой причиной выявленных угроз.
Проектируемая система переходит к модели
с централизованным эмитентом и распределённой верификацией:
единственный сервис выпускает токены и владеет закрытым ключом,
а все микросервисы верифицируют токены с помощью открытого ключа,
не имея возможности выпускать новые.
Это устраняет угрозы подмены идентичности, подделки данных
и повышения привилегий,
а также делает возможной автоматическую ротацию ключей.

\section{Доменная модель системы авторизации}\label{sec:domain-model}

Прежде чем проектировать архитектуру,
необходимо определить доменную модель~---
набор сущностей, которыми будет оперировать система.
Каждая сущность вводится исходя из конкретной задачи,
которую она призвана решить.

Централизация выпуска токенов предполагает,
что система должна знать, \emph{кому} она выдаёт токены
и \emph{с какими} параметрами.
Для этого вводится сущность \textbf{клиент авторизации} (\texttt{auth\_clients})~---
зарегистрированный микросервис или внешняя система,
имеющие право запрашивать токены.
Каждый клиент идентифицируется уникальным \texttt{client\_id}
и содержит набор обязательных утверждений (\texttt{enforced\_claims})~---
пар <<ключ-значение>>, которые должны присутствовать
во входящем токене запрашивающей стороны,
чтобы та могла выпустить токен от имени данного клиента.

Один и тот же клиент может обращаться к нескольким микросервисам,
каждый из которых требует собственного набора разрешений.
Для описания этих вариантов вводится сущность
\textbf{политика токенов} (\texttt{token\_policies}),
привязанная к клиенту.
Политика определяет время жизни, список разрешений
и версию, позволяющую обнаруживать изменения конфигурации.

Ряд внешних систем (Grafana, Make) не поддерживают JWT
и могут аутентифицироваться только статическим секретом.
Для таких случаев предусмотрена сущность
\textbf{API-ключ} (\texttt{api\_keys}),
привязанная к клиенту и имеющая собственный жизненный цикл
с отслеживанием даты последней ротации.

Система должна принимать запросы не от любого источника,
а только от заранее определённых доверенных систем~---
Kubernetes-кластеров, GitLab CI, Octopus Deploy
и других экземпляров микросервиса авторизации.
Для этого вводится сущность
\textbf{доверенный эмитент} (\texttt{trusted\_issuers}),
описывающая внешнюю систему, способ получения её публичных ключей
и группу доступа, определяющую, к каким эндпоинтам системы авторизации
данный эмитент имеет доступ.

Процесс ротации ключей состоит из нескольких шагов
и должен переживать перезапуски подов и инфраструктурные сбои.
Для сохранения состояния между шагами вводится сущность
\textbf{ротация ключей} (\texttt{rsa\_rotations}),
хранящая текущий шаг, статус, источник запуска
и счётчики pause-пингов.

Наконец, для выполнения требования наблюдаемости
необходим аудиторский след всех значимых действий:
выпуска токенов, изменения конфигурации, ротации ключей.
Для этого вводится сущность
\textbf{журнал событий} (\texttt{event\_log\_entries}),
используемая для доставки событий в SIEM.

\section{Архитектура микросервиса}\label{sec:architecture}

Далее проектируемый микросервис авторизации
будет именоваться \textbf{auth-jwt}.
Он будет следовать слоистой архитектуре~\cite{Fowler2002PEAA}
с инверсией зависимостей:
общий слой бизнес-логики и доступа к данным
не будет зависеть от точек входа (HTTP API, фоновые задачи),
а взаимодействие с внешними системами
будет описано интерфейсами,
что позволит заменять реализации без изменения бизнес-логики.
Выбор обусловлен двумя факторами:
все микросервисы Mindbox следуют этой архитектуре,
что снижает порог входа для команд, которые будут поддерживать систему;
а доменная область микросервиса авторизации не настолько сложна,
чтобы оправдать переход к более тяжёлым архитектурным стилям.

Кодовая база будет разделена на четыре компонента (\firef{fig:microservice-arch}).

\begin{itemize}
  \item \textbf{Model}~--- нижний слой, содержащий бизнес-логику,
    сущности, репозитории и доступ к данным.
    Будет включать логику ротации ключей, генерации токенов,
    работу с хранилищем секретов и очередью событий.
    Этот слой не будет зависеть от веб-фреймворка,
    что позволит использовать его как из HTTP API, так и из фонового процесса.

  \item \textbf{Services}~--- верхний слой, реализующий HTTP API.
    Будет принимать запросы на генерацию JWT,
    публиковать открытые ключи через JWKS endpoint,
    предоставлять API для управления клиентами и доверенными эмитентами,
    а также выпускать токены разработчикам.
    Зависит от Model и использует его для выполнения бизнес-операций.

  \item \textbf{Worker}~--- верхний слой, реализующий фоновые задачи:
    ротацию ключей подписи,
    доставку событий из журнала в SIEM,
    сбор метрик и автоматическое восстановление зависших ротаций.
    Зависит от того же слоя Model, что и Services.
    Состояние планировщика будет храниться в базе данных,
    что обеспечит корректное возобновление задач при рестарте пода.

  \item \textbf{Migrator}~--- утилита управления схемой базы данных.
    Будет выполнять миграции при деплое перед запуском остальных компонентов,
    гарантируя согласованность схемы с кодовой базой.
\end{itemize}

\begin{figure}[ht!]
  \centering
  \includegraphics[width=0.85\textwidth]{diagrams/img/ch2_microservice_arch}
  \caption{Компоненты auth-jwt}
  \label{fig:microservice-arch}
\end{figure}

Services и Worker будут разделять общий слой Model,
но масштабироваться независимо,
поскольку профили нагрузки у них принципиально различаются:
Services обрабатывает синхронные HTTP-запросы,
а Worker~--- периодические фоновые задачи.

\section{Аутентификация запросов к auth-jwt}\label{sec:auth-requests}

Микросервис авторизации не будет выдавать токены анонимным запросам~---
каждая запрашивающая сторона должна будет пройти аутентификацию.
В существующих системах авторизации применяются три основных способа
аутентификации клиентов~\cite{RFC6749}:

\begin{itemize}
  \item \textbf{Client Secret}~--- клиент передаёт предварительно выданный секрет.
    Способ прост в реализации,
    но требует безопасного хранения и ротации секрета на стороне клиента.
  \item \textbf{mTLS}~--- взаимная аутентификация по сертификатам
    на транспортном уровне.
    Обеспечивает высокую безопасность,
    но предполагает наличие PKI-инфраструктуры.
  \item \textbf{Аутентификация по токену эмитента}~--- клиент предъявляет JWT,
    подписанный ключом доверенной системы.
    Микросервис авторизации проверяет подпись по заранее известному публичному ключу этой системы.
\end{itemize}

В контексте платформы Mindbox ключевым наблюдением является то,
что все системы, которым потребуется запрашивать токены,
уже выпускают собственные подписанные JWT~---
Kubernetes, GitLab CI, Octopus Deploy.
Более того, эти системы следуют стандарту OIDC~\cite{OpenIDConnect}
и публикуют свои открытые ключи через OIDC Discovery endpoint.

Это означает, что микросервис авторизации сможет аутентифицировать запросы
по токенам этих систем без необходимости выдавать и ротировать
отдельные секреты для каждого потребителя.
Достаточно зарегистрировать систему как доверенного эмитента
и периодически обновлять её публичные ключи.

\section{Доверенные эмитенты}\label{sec:trust}

На основе описанного подхода проектируется
механизм доверенных эмитентов (trusted issuers).
Каждый эмитент будет привязан к группе доступа,
определяющей, к каким эндпоинтам микросервиса авторизации
будут допущены запросы, подписанные токенами этого эмитента.

\subsection{Получение и обновление публичных ключей}\label{subsec:key-fetching}

Для проверки подписи входящих токенов
микросервис авторизации будет хранить публичные ключи каждого доверенного эмитента.
Поскольку эмитенты следуют стандарту OIDC~\cite{OpenIDConnect},
их ключи будут получаться автоматически
через OIDC Discovery endpoint (\firef{fig:key-fetching}).

Фоновая задача будет периодически опрашивать Discovery endpoint каждого эмитента
и обновлять кеш публичных ключей.
При поступлении запроса обращения к эмитенту не будет~---
проверка подписи выполнится по кешированным ключам.
Если эмитент временно недоступен,
будет использоваться последняя успешно загруженная версия ключей.
Это обеспечит устойчивость к кратковременным сбоям внешних систем:
микросервис авторизации продолжит принимать и проверять токены
даже при недоступности эмитента.

\subsection{Процесс аутентификации входящего запроса}\label{subsec:auth-flow}

При поступлении запроса auth-jwt будет выполнять следующие шаги
(\firef{fig:trust-auth}):

\begin{enumerate}
  \item Определить, какие группы доступа разрешены для вызываемого эндпоинта.
  \item Загрузить из кеша публичные ключи всех доверенных эмитентов,
    принадлежащих этим группам.
  \item Отфильтровать эмитентов по значению issuer во входящем токене.
  \item Последовательно попытаться проверить подпись токена
    ключами оставшихся эмитентов.
  \item При первом успешном результате~--- считать аутентификацию пройденной.
  \item Авторизовать запрос: проверить enforced claims клиента.
    Если обязательные утверждения не совпадают~--- отклонить запрос.
\end{enumerate}

\section{Механизм доставки данных авторизации}\label{sec:delivery}

Централизация выпуска токенов создаёт новую проблему:
если каждый из 160~микросервисов при каждом запросе
будет обращаться к auth-jwt,
тот станет единой точкой отказа~---
его недоступность парализует всю платформу.
Необходимо спроектировать механизм,
при котором микросервисы будут получать актуальные токены и публичные ключи,
но не будут зависеть от доступности auth-jwt в момент обработки запроса.
Рассмотрим три подхода.

\textbf{Прямые запросы от микросервисов.}
Каждый микросервис самостоятельно запрашивает токены и ключи у auth-jwt
и кеширует их локально.
Достоинство: не требуется дополнительных компонентов.
Недостаток: у микросервисов платформы могут быть десятки и сотни реплик,
и каждая из них будет отправлять запросы к auth-jwt.
При 160~микросервисах с несколькими репликами каждого
суммарная нагрузка может достигать тысяч запросов в секунду,
что превращает auth-jwt в узкое место.
Кроме того, при недоступности auth-jwt микросервисы
не смогут получить новые токены до истечения кеша (\firef{fig:delivery-direct}).

\begin{figure}[ht!]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/ch2_delivery_direct.drawio}
  \caption{Прямые запросы: каждая реплика обращается к auth-jwt}
  \label{fig:delivery-direct}
\end{figure}

\textbf{Агент}~--- отдельное приложение,
развёрнутое для каждого микросервиса.
Агент будет периодически запрашивать данные авторизации у auth-jwt
и записывать их в Kubernetes Secret, доступный всем репликам микросервиса.
Достоинство: микросервисы не обращаются к auth-jwt напрямую,
а количество запросов определяется числом микросервисов, а не реплик.
Недостаток: каждый агент~--- отдельный под с потреблением CPU и памяти.
При 160~микросервисах и порядка 900~CDP-клиентов в одном контуре
потребуется более 1000~экземпляров агента.
При потреблении около 50~МБ памяти на экземпляр
суммарный расход составит более 50~ГБ в каждом контуре
только на агентов авторизации, что является неприемлемо дорогим решением
(\firef{fig:delivery-agent}).

\begin{figure}[ht!]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/ch2_delivery_agent.drawio}
  \caption{Агент: отдельный экземпляр на каждый микросервис}
  \label{fig:delivery-agent}
\end{figure}

\textbf{Kubernetes-оператор}~--- единственный компонент на кластер,
который будет следить за декларативными спецификациями (Custom Resource)
и записывать данные авторизации в Kubernetes Secret (\firef{fig:operator-delivery}).
Достоинство: один экземпляр оператора обслужит все микросервисы кластера
независимо от числа их реплик;
микросервисы будут читать файл из Secret, не выполняя HTTP-запросы.
Недостаток: дополнительный Custom Resource Definition в кластере.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/ch2_delivery_operator.drawio}
  \caption{Доставка токенов и JWKS через Kubernetes-оператор}
  \label{fig:operator-delivery}
\end{figure}

Для проектируемой системы выбран подход с оператором,
поскольку он минимизирует нагрузку на auth-jwt
и не требует модификации подов микросервисов.
Оператор будет выполнять reconcile-цикл с коротким интервалом:
читать спецификацию из Custom Resource,
запрашивать токены и JWKS у auth-jwt
и записывать результат в Kubernetes Secret.
Микросервисы будут читать этот файл через клиентскую библиотеку,
которая будет отслеживать изменения автоматически.

Для токенов, требующих данных из рантайма (например, идентификатор тенанта),
будет предусмотрен второй режим~--- прямой запрос к auth-jwt
с встроенным in-memory кешем и автоматической инвалидацией при ротации.

Характеристики двух режимов приведены в \taref{tab:token-modes}.

\section{Клиентская библиотека}\label{sec:client-library}

В текущей системе все микросервисы используют библиотеку
\texttt{Mindbox.Authentication} для работы с авторизацией.
При переходе на новую систему эта библиотека будет существенно переработана
для поддержки нового механизма.

Основные функции библиотеки в новой версии:
\begin{itemize}
  \item Проверка подписи и срока действия JWT на входящих запросах
    по публичным ключам из Kubernetes Secret.
  \item Автоматическая подстановка JWT в исходящие HTTP-запросы.
  \item Чтение токенов из Kubernetes Secret для статического режима.
  \item Получение токенов напрямую от auth-jwt для динамического режима
    с встроенным кешированием.
  \item Обнаружение ротации ключей: при несовпадении идентификатора ключа
    в токене и в JWKS библиотека инвалидирует кеш
    и запросит актуальные данные.
\end{itemize}

Благодаря тому, что библиотека уже интегрирована во все микросервисы,
переход на новую систему авторизации не потребует
изменения кода каждого микросервиса~---
достаточно будет обновить версию библиотеки и конфигурацию.

\section{Проектирование процесса ротации ключей}\label{sec:rotation-design}

Процесс ротации будет состоять из трёх шагов с двумя паузами между ними
(\firef{fig:rotation-sequence}).
Каждый шаг будет изменять состояние ключей в хранилище,
а паузы~--- обеспечивать время для распространения обновлений по системе.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/ch2_rotation_sequence}
  \caption{Последовательность ротации ключей подписи}
  \label{fig:rotation-sequence}
\end{figure}

\textbf{Шаг~1. Создание нового ключа.}
Генерируется новый ключ (Ключ~B)
и записывается в хранилище как SECONDARY.
PRIMARY (Ключ~A) продолжает использоваться для подписи.
Оба ключа публикуются через JWKS endpoint.

\textbf{Пауза~1. Ожидание доставки JWKS.}
Оператор должен доставить обновлённый JWKS
(содержащий оба ключа) до всех микросервисов.
Пока микросервисы не знают о Ключе~B,
переключать подпись нельзя~--- новые токены не пройдут проверку.

\textbf{Шаг~2. Swap ключей.}
PRIMARY и SECONDARY меняются местами:
Ключ~B становится PRIMARY, Ключ~A~--- SECONDARY.
С этого момента новые токены подписываются Ключом~B.
Токены, подписанные Ключом~A, остаются валидными~---
микросервисы проверяют подпись обоими ключами.

\textbf{Пауза~2. Ожидание обновления токенов.}
Токены, подписанные старым ключом, должны выйти из обращения.
Оператор обновит токены в Secret,
а клиентская библиотека обнаружит несовпадение идентификатора ключа
и запросит актуальный токен.

\textbf{Шаг~3. Удаление старого ключа.}
SECONDARY (Ключ~A) удаляется из хранилища.
В системе снова один активный ключ.

\subsection{Ping-механизм и устойчивость к сбоям}\label{subsec:ping}

Паузы между шагами будут реализованы не через фиксированное ожидание,
а через ping-механизм:
на каждой итерации система будет выполнять HTTP-запрос к собственному JWKS endpoint.
При успешном ответе счётчик пингов будет инкрементироваться.
Для перехода к следующему шагу потребуется заданное число успешных пингов.
Счётчик будет храниться в базе данных,
поэтому прогресс не потеряется при рестарте пода.

Такой подход обеспечит устойчивость к инфраструктурным сбоям:
при отказе зоны доступности пинги не пройдут
и ротация автоматически приостановится до восстановления;
при недоступности хранилища ключей шаг завершится с ошибкой,
но существующие ключи останутся нетронутыми.
Дополнительно будет предусмотрена фоновая задача,
которая периодически обнаруживает зависшие ротации и перезапускает их.

\subsection{Инварианты ротации}\label{subsec:invariants}

Корректность ротации будет гарантироваться пятью инвариантами:
\begin{enumerate}
  \item Токены всегда подписываются PRIMARY-ключом.
  \item Проверка подписи выполняется по всем активным ключам (PRIMARY + SECONDARY).
  \item Закрытые ключи хранятся только в хранилище секретов;
    доступ будет иметь только auth-jwt.
  \item Открытые ключи будут доступны через JWKS endpoint
    и через оператор (в Kubernetes Secret).
  \item В любой момент времени активно не более двух ключей.
\end{enumerate}

\subsection{SLO и расписание ротации}\label{subsec:rotation-schedule}

На ротацию планируется установить SLO~--- 30~минут на полный цикл.
Превышение этого порога будет вызывать предупреждающий алерт.
Если ключи не будут ротироваться более 8~дней,
сработает критический алерт.

Расписание ротации будет привязано к техническому окну обслуживания

Продуктивные контуры будут ротироваться еженедельно,
а тестовые~--- ежедневно для раннего обнаружения проблем.

\section{Межконтурное взаимодействие}\label{sec:exchange}

В предыдущих разделах описан механизм авторизации
в рамках одного контура.
Однако микросервисы Mindbox нередко обращаются к сервисам в других контурах~---
например, к административным сервисам на контуре Infra.

При проектировании необходимо решить:
будет ли у всех контуров один общий экземпляр auth-jwt с общими ключами
или у каждого контура будет собственный экземпляр с отдельными ключами.

Общий экземпляр проще в эксплуатации,
однако нарушает принцип изоляции контуров:
компрометация ключа затронет все контуры одновременно~---
именно та проблема, которая выявлена в текущей системе.
Поэтому каждый контур будет иметь собственный экземпляр auth-jwt
с отдельными ключами подписи.
Токен, выпущенный в одном контуре, будет невалиден в другом.

Возникает вопрос: каким образом микросервис одного контура
сможет авторизоваться в другом, если ключи различаются?
В первой главе был рассмотрен стандарт Token Exchange~\cite{RFC8693},
позволяющий обменять один токен безопасности на другой
у службы авторизации.
Поскольку auth-jwt каждого контура будет реализовывать
стандарт OIDC~\cite{OpenIDConnect}~---
публиковать свои ключи через Discovery endpoint,~---
экземпляр auth-jwt одного контура сможет выступать
доверенным эмитентом для экземпляра другого контура.
Это позволит реализовать Token Exchange между контурами:
auth-jwt исходного контура выпустит exchange-токен,
а auth-jwt целевого контура проверит его подпись
по публичным ключам исходного контура, полученным через OIDC Discovery
(\firef{fig:exchange-sequence}).

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/ch2_exchange_sequence}
  \caption{Межконтурная авторизация через Token Exchange}
  \label{fig:exchange-sequence}
\end{figure}

Процесс будет состоять из трёх этапов.
На первом этапе микросервис получит exchange-токен
у auth-jwt своего контура~---
JWT с коротким временем жизни, пригодный исключительно для обмена.
На втором этапе exchange-токен будет предъявлен
Микросервис авторизации целевого контура
проверит подпись по публичным ключам исходного контура
и выпустит токен целевого контура.
На третьем этапе полученный токен будет использован
для авторизованного запроса к микросервису целевого контура.

Для реализации exchange в целевом контуре будет создаваться
выделенный exchange-клиент, связанный с исходным клиентом.
Микросервис авторизации целевого контура выдаст токены exchange-клиента
только если запрос придёт от связанного исходного клиента.

При работе через оператор exchange будет выполняться автоматически~---
микросервису не нужно будет знать о механизме обмена.
В Kubernetes Secret будет записан готовый токен целевого контура.

\section{Управление конфигурацией через IaC}\label{sec:iac-management}

Конфигурация системы авторизации~---
клиенты, политики, доверенные эмитенты, exchange-правила~---
будет управляться исключительно через Terraform.
Для этого планируется разработать два компонента:
Terraform Provider, реализующий CRUD-операции через API auth-jwt,
и Terraform-модуль, содержащий конфигурацию всех клиентов платформы.

Terraform-модуль станет единственным источником истины
о конфигурации авторизации.
Изменения будут проходить стандартный цикл разработки:
ветвление, code review, применение через CI/CD-пайплайн.

Такой подход обеспечит воспроизводимость конфигурации на всех контурах,
полную историю изменений в Git
и возможность рецензирования каждого изменения.

\section{Подбор инструментальных средств}\label{sec:tools}

Выбор инструментальных средств определяется
техническими требованиями из раздела~\ref{sec:requirements},
существующей экспертизой команды и готовностью инфраструктуры.

\textbf{PostgreSQL}~--- основная база данных системы.
Будет хранить конфигурацию клиентов, политики, доверенных эмитентов,
состояние ротации и журнал событий.
Выбор обусловлен тремя факторами:
в компании накоплена экспертиза по эксплуатации PostgreSQL,
готова инфраструктура развёртывания,
а ожидаемый характер нагрузки (простые запросы по первичному ключу)
не требует специализированных решений.

\textbf{HashiCorp Vault}~\cite{HashiCorpVault}~--- хранилище закрытых ключей.
Доступ к Vault будет иметь исключительно auth-jwt~---
ни один другой микросервис не сможет прочитать закрытый ключ.
Vault уже используется в платформе для управления секретами,
что позволит задействовать существующую инфраструктуру и экспертизу.

\textbf{Dragonfly}~--- распределённый кеш, совместимый с протоколом Redis.
Планируется использовать для кеширования конфигурации клиентов
по принципу многоуровневого кеша (\firef{fig:cache-layers}):
in-memory кеш как L1, Dragonfly как L2, PostgreSQL как L3.
Выбор Dragonfly обусловлен более высокой производительностью
по сравнению с Redis при многопоточной нагрузке
и полной совместимостью с существующими клиентскими библиотеками.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.8\textwidth]{diagrams/img/ch2_cache_layers}
  \caption{Трёхуровневая схема кеширования}
  \label{fig:cache-layers}
\end{figure}

\textbf{C\#}~--- язык реализации auth-jwt и клиентской библиотеки.
Является стандартом разработки в компании.
Экосистема .NET предоставляет развитые библиотеки
для работы с аутентификацией и авторизацией,
что позволит сократить объём собственного кода.

\textbf{Go}~--- язык реализации Kubernetes-оператора и Terraform Provider.
Выбор обусловлен наличием Operator SDK~---
официальной библиотеки для разработки операторов,
а также тем, что Terraform Provider SDK доступен исключительно на Go.

\textbf{Kafka}~--- очередь для доставки событий в SIEM.
Микросервис авторизации не будет писать в Kafka напрямую~---
планируется использовать Outbox-паттерн (\firef{fig:outbox}):
события будут сохраняться в таблицу журнала в базе данных
в той же транзакции, что и основное действие,
а фоновая задача будет читать необработанные события и отправлять их в Kafka.
Такой подход гарантирует согласованность~---
событие запишется только при успешном завершении операции.

  \caption{Outbox-паттерн доставки событий в Kafka}
  \label{fig:outbox}
\end{figure}

\textbf{Quartz.NET}~--- планировщик фоновых задач.
Будет использоваться для выполнения ротации по расписанию,
обработки журнала событий и сбора метрик.
Состояние планировщика будет храниться в PostgreSQL,
что обеспечит корректную работу при рестартах пода.

Для интеграционного тестирования планируется использовать Testcontainers~---
PostgreSQL, Vault и Dragonfly будут подниматься в контейнерах,
что обеспечит воспроизводимость тестового окружения.

\section{Наблюдаемость}\label{sec:observability}

Для выполнения требования~8 (наблюдаемость)
система будет предоставлять метрики в формате Prometheus.
Метрики планируется разделить на четыре группы.

\textbf{Генерация токенов.}
Будут отслеживаться задержка генерации на 95-м процентиле

\textbf{Ротация ключей.}

\textbf{Оператор.}
Будут контролироваться наличие reconcile-циклов,
время их выполнения и статусы полученных токенов.

\textbf{Доверенные эмитенты.}
Будет отслеживаться успешность получения публичных ключей
от каждого эмитента.

\section{Выводы по главе}\label{sec:ch2-conclusion}

В данной главе спроектирована архитектура системы авторизации auth-jwt.
