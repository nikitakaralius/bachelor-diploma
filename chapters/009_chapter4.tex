\chapter{Тестирование и апробация}\label{ch4}

Данная глава закрывает две задачи из введения:
разработку и тестирование компонентов системы
и апробацию системы в промышленной среде.
Сначала обозначается общая стратегия тестирования
и устройство конвейера непрерывной интеграции.
Затем последовательно рассматриваются тесты каждого
из четырёх компонентов системы:
auth-jwt, Kubernetes-оператора, Terraform-провайдера
и клиентской библиотеки.
Далее приводятся результаты нагрузочного тестирования auth-jwt
и описывается хаос-инжиниринг в промышленной среде.
В заключение приводится результат апробации
после внедрения системы в эксплуатацию.

\section{Стратегия тестирования}\label{sec:ch4-strategy}

Система состоит из четырёх компонентов разной природы:
прикладной микросервис auth-jwt на C\#,
Kubernetes-оператор на Go,
Terraform-провайдер на Go
и клиентская библиотека Mindbox.Authentication на C\#.
Соответственно различается и стратегия тестирования каждого
из них~--- единого подхода, одинаково эффективного
для всех компонентов, не существует.

Классическая пирамида тестов~\cite{Cohn2009}
предписывает массовое использование юнит-тестов в основании,
меньшее количество интеграционных в середине
и небольшое число сквозных (end-to-end) тестов на вершине.
Такое распределение оптимизирует время прогона:
юнит-тесты исполняются за миллисекунды,
тогда как E2E-тесты~--- за секунды или минуты.
Однако пирамида плохо подходит для инфраструктурного кода.
Существенная часть логики auth-jwt и оператора~---
это связующий код между внешними системами:
PostgreSQL, HashiCorp Vault, Kubernetes API.
Юнит-тестирование такого кода требует мокирования внешних систем,
а моки воспроизводят лишь предположения разработчика о поведении
зависимости, а не само поведение.
Эмпирическое исследование~\cite{InozemtsevaHolmes2014}
показывает, что покрытие кода тестами слабо коррелирует
со способностью тест-сьюта обнаруживать реальные дефекты:
важнее не доля юнит-тестов, а адекватность тестов поведению системы.

С учётом сказанного для auth-jwt и клиентской библиотеки
основная масса тестов~--- интеграционные:
auth-jwt тестируется с реальными PostgreSQL и Vault,
поднятыми через Testcontainers;
клиентская библиотека~--- с реальным ASP.NET~Core
через \texttt{TestWebApplicationFactory}.
Для Kubernetes-оператора применяется E2E-тестирование
на встроенном в контейнер кластере Kind с fake-реализацией
интерфейса auth-jwt~--- юнит-тесты здесь дают слабые гарантии
из-за плотного взаимодействия с Kubernetes API.
Для Terraform-провайдера достаточно юнит-тестирования
схемы и преобразований: ключевые сценарии его применения
(создание клиента, ротация ключей)
уже косвенно покрываются E2E-тестами оператора
и интеграционными тестами auth-jwt.

\subsection{Микросервис auth-jwt}\label{subsec:ch4-auth-jwt-tests}

Для интеграционного тестирования auth-jwt разработан
предметно-ориентированный язык (Domain-Specific Language, DSL),
позволяющий описывать тесты лаконично
даже для сложного функционала.
DSL состоит из трёх слоёв:
прямые операции с базой данных,
операции через HTTP API
и операции с секретами в Vault.

В листинге~\ref{lst:integration-test} приведён
пример теста генерации токена.

\begin{lstlisting}[language={[Sharp]C},
  label={lst:integration-test},
  caption={Интеграционный тест генерации токена с использованием DSL}]
[TestMethod]
public async Task GenerateToken_ValidParameters_TokenGenerated()
{
    // Arrange: создание клиента через DSL
    var client = BuildAuthClient(TestClientId,
        tokenPolicies: [BuildPolicy(TestPolicy,
            permissions: ["ReadSomething"],
            allowTenantHeader: true)]);
    await AuthClientsDb.CreateAsync(client);
    var k8sToken = GetK8STokenFake(TestClientId);

    // Act: запрос токена через HTTP
    using var content = JsonContent.Create(
        new ClientTokenRequest {
            ClientId = TestClientId,
            Tenant = "testTenant",
            Policy = TestPolicy });
    var response = await ServicesProject.SendAsync<TokenResponse>(
        "/token", HttpMethod.Post, content, token: k8sToken);

    // Assert: проверка claims и метрик
    var jwt = ReadJsonWebToken(response.Token);
    Assert.AreEqual(TestClientId, jwt.Subject);
    AssertClaim(jwt, MindboxJwtConstants.TenantClaim, "testTenant");

    var metricValue = _tokenIssuedCounter
        .WithLabels(TestClientId, TestPolicy, "testTenant").Value;
    Assert.AreEqual(1, metricValue);
}
\end{lstlisting}

Тест читается как спецификация:
создать клиента с политикой,
запросить токен,
проверить содержимое и метрику.
Вспомогательные методы \texttt{BuildAuthClient},
\texttt{BuildPolicy}, \texttt{GetK8STokenFake}
скрывают подготовку инфраструктуры,
а \texttt{AssertClaim}~--- типовые проверки JWT.
Помимо содержимого токена, тест проверяет,
что метрика Prometheus была инкрементирована~---
это гарантирует наблюдаемость.

\subsection{Kubernetes-оператор}\label{subsec:ch4-operator-tests}

Для end-to-end тестирования оператора используется
фреймворк Ginkgo~--- BDD-фреймворк для Go.
Тесты запускают Kind-кластер (Kubernetes в контейнере),
разворачивают оператор с fake backend
и проверяют реальное поведение системы.

В листинге~\ref{lst:e2e-test} приведён сокращённый тест,
проверяющий, что удалённые из CR токены
остаются в Secret до истечения срока действия.

\begin{lstlisting}[language=Go,
  label={lst:e2e-test},
  caption={E2E-тест: удалённые токены остаются в Secret до истечения TTL}]
It("deleting tokens from CR does not remove from secret "+
    "until expiration", func() {

    By("applying valid AuthJwtConfig")
    cmd.ApplyAuthJwtConfig(authjwtv1.AuthJwtConfig{
        Spec: authjwtv1.AuthJwtConfigSpec{
            Contour:    "stable",
            SecretName: secretName,
            Tokens: []authjwtv1.TokenSpec{{
                Name:   "api-token",
                Policy: authjwt.FakeShortLivedPolicy,
            }},
        },
    })

    By("awaiting first reconcile")
    waitForFirstReconcile(clientNS, clientName)

    By("removing tokens from spec")
    cmd.ApplyAuthJwtConfig(authjwtv1.AuthJwtConfig{
        Spec: authjwtv1.AuthJwtConfigSpec{
            Contour: "stable", SecretName: secretName,
            Tokens:  []authjwtv1.TokenSpec{},
        },
    })

    By("checking token remains in secret")
    Consistently(func(g Gomega) {
        secret, _ := cmd.GetAuthSecretData(clientNS, secretName)
        g.Expect(secret.Tokens).To(HaveKey("api-token"))
    }, 2*time.Second, 200*time.Millisecond).Should(Succeed())

    By("waiting for secret removal after expiration")
    Eventually(func(g Gomega) {
        secret, _ := cmd.GetAuthSecretData(clientNS, secretName)
        g.Expect(secret.Tokens).NotTo(HaveKey("api-token"))
    }).Should(Succeed())
})
\end{lstlisting}

Тест использует две ключевые конструкции Ginkgo:
\texttt{Consistently}~--- утверждает, что условие выполняется
непрерывно в течение заданного интервала;
\texttt{Eventually}~--- ожидает выполнения условия с таймаутом.

\subsection{Terraform-провайдер}\label{subsec:ch4-terraform-tests}

Terraform-провайдер представляет собой тонкий слой между
конфигурацией пользователя и HTTP API микросервиса auth-jwt:
независимой бизнес-логики в нём практически нет,
а основные обязанности~--- маппинг состояния ресурса
в запросы к API и обратно, валидация схемы конфигурации
и собственно выполнение HTTP-запросов.
В соответствии с этим юнит-тесты группируются в три блока.

\textbf{Маппинг плана и состояния.}
Чистые функции \texttt{mapApiResponseToState},
\texttt{mapPlanToCreateRequest} и \texttt{mapPlanToUpdateRequest}
переводят данные между внутренним представлением Terraform
(типы \texttt{types.String}, \texttt{types.Set}, \texttt{types.Object})
и DTO для HTTP-запросов.
Тестируются как полные сценарии (все поля заданы),
так и граничные случаи: пустые наборы прав,
отсутствующий блок API-ключей, опциональные поля валидатора аудитории.
Пример теста маппинга приведён в листинге~\ref{lst:tf-map-test}.

\begin{lstlisting}[language=Go,
  label={lst:tf-map-test},
  caption={Юнит-тест маппинга API-ответа в состояние ресурса}]
state, diags := mapApiResponseToState(&AuthClientResponse{
    ClientID:          "client-a",
    AllowCustomClaims: true,
    EnforcedClaims:    map[string][]string{"iss": {"issuer-a"}},
    TokenPolicies: map[string]TokenPolicyDto{
        "default": {TTLSeconds: 3600,
                    Permissions: []string{"read", "write"}},
    },
})
if diags.HasError() { t.Fatalf("unexpected: %v", diags) }
if state.ClientID.ValueString() != "client-a" { t.Fatal() }
if state.TokenPolicies["default"].TTLSeconds.ValueInt32() != 3600 {
    t.Fatal()
}
\end{lstlisting}

\textbf{Кастомные валидаторы схемы.}
Тип ресурса доверенного эмитента (trusted issuer) допускает
несколько вариантов хранения публичных ключей: OIDC discovery,
прямой список ключей AuthJwt или JWKS endpoint.
Каждому варианту соответствует свой блок конфигурации,
обязательный только при определённом значении поля
\texttt{storage\_type}.
Эту зависимость выражает кастомный валидатор
\texttt{RequiredWhenStorageType}, который проверяется таблицей
сценариев: блок присутствует при подходящем типе,
блок отсутствует при подходящем типе (ошибка),
блок отсутствует при чужом типе (валидно).

\textbf{HTTP-клиент к auth-jwt.}
CRUD-операции и обмен токенами тестируются против
\texttt{httptest.Server}~--- встроенного в стандартную библиотеку Go
мока HTTP-сервера, работающего в том же процессе, что и тест.
Мок-сервер регистрирует обработчики путей \texttt{/token},
\texttt{/clients}, \texttt{/trusted-issuers},
имитирует ответы auth-jwt в нужном формате
и валидирует заголовок \texttt{Authorization}.
Покрытые сценарии: успешные CRUD, обмен внешнего токена на внутренний,
обёртывание HTTP-ошибок в типизированный \texttt{APIError},
обработка некорректного JSON в ответе
и валидация \texttt{nil} HTTP-клиента.

Acceptance-тесты, требующие реального экземпляра auth-jwt
с PostgreSQL и Vault, в провайдере не используются.
Это сознательный выбор: бизнес-сценарии применения провайдера
(создание клиента, регистрация доверенного эмитента, ротация ключей)
уже покрываются интеграционными тестами auth-jwt
и E2E-тестами Kubernetes-оператора, который использует
тот же HTTP API.
Acceptance-тесты дублировали бы эти проверки
ценой поднятия полной инфраструктуры на каждый прогон CI,
тогда как тесты на \texttt{httptest.Server} исполняются за секунды
и достаточны для верификации контрактной зоны провайдера.

\section{Нагрузочное тестирование auth-jwt}\label{sec:ch4-load}

Цель нагрузочного тестирования~--- оценить запас по производительности
относительно SLO на генерацию токена~--- не более 30~мс
по 95-му процентилю.
Тестируется именно auth-jwt:
оператор и клиентская библиотека работают с локальными ресурсами
(Kubernetes API и файловой системой соответственно)
и не лежат на горячем пути авторизации запросов.

Инструментом выбран Grafana~k6~---
open-source-фреймворк нагрузочного тестирования
со сценариями на JavaScript и нативным экспортом метрик в Prometheus.
Преимущество k6~--- единая модель сценариев, агентов и отчётности,
без отдельного агрегатора и сбора результатов вручную.
Стенд развёртывается в изолированном Kubernetes-namespace
и включает auth-jwt, PostgreSQL и HashiCorp Vault~---
все три зависимости поднимаются в реальных версиях,
без подмены моками.
Сценарий имитирует штатный путь авторизации запросов:
запрос токена через \texttt{POST /token}
с уже зарегистрированным клиентом и прогретым кешем подписи.

Целевой график нагрузки~--- линейный рост RPS до точки,
в которой либо нарушается SLO,
либо инструмент перестаёт выдавать заданный rate.
В проведённых прогонах генератор достиг 15~000~RPS,
после чего пиковая нагрузка упёрлась в производительность самого k6;
auth-jwt продолжал отвечать без отказов.
На пике 95-й процентиль времени ответа составил 80~мс,
что выше SLO 30~мс, но соответствует нагрузке,
существенно превосходящей промышленную (см.~ниже).
Точка деградации auth-jwt~--- значение RPS,
при котором сервис теряет способность держать SLO~---
в эксперименте не достигнута.
График зависимости времени ответа от подаваемой нагрузки
приведён на \firef{fig:k6-load}.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/k6-load.png}
  \caption{Нагрузочное тестирование auth-jwt в Grafana k6: RPS и время ответа}
  \label{fig:k6-load}

Результаты нагрузочного тестирования следует сопоставлять
с реальной нагрузкой контуров платформы.
На контуре Gamma~--- максимальном по входящему трафику~---
наблюдаемая нагрузка на auth-jwt не превышает примерно 150~RPS,
а 95-й процентиль времени ответа держится на уровне 8~мс
(детально показатели промышленной эксплуатации
приводятся в~\ref{sec:ch4-rollout}, \firef{fig:gamma-usage}).
Низкий уровень нагрузки на auth-jwt относительно числа
обрабатываемых платформой запросов
является прямым следствием архитектурных решений из главы~\ref{ch3}:
оператор выпускает токены пачками и кладёт их в Secret,
а клиентская библиотека держит токены в локальном кеше
до момента упреждающего обновления.
В результате к auth-jwt обращается не каждый запрос платформы,
а только клиентская библиотека~--- по факту истечения буфера токена.

Из приведённых данных следует два вывода.
Во-первых, в промышленной эксплуатации SLO выдерживается
с запасом почти в четыре раза
(8~мс по факту против допустимых 30~мс).
Во-вторых, кратное увеличение нагрузки до уровня,
в сто раз превышающего наблюдаемый промышленный пик,
не выводит auth-jwt из строя~---
сервис продолжает отвечать в пределах десятков миллисекунд,
а нарушение SLO в пиковом сценарии нагрузочного теста
не означает деградации в производственной эксплуатации.
Из обнаруженного разрыва между промышленной нагрузкой
и пропускной способностью сервиса вытекает практическое следствие
для размера выделяемых auth-jwt ресурсов, которое рассматривается
в~\ref{sec:ch4-rollout}.

\section{Хаос-инжиниринг в промышленной среде}\label{sec:ch4-chaos}

Автоматизированные тесты в CI проверяют корректность системы
относительно зафиксированного набора сценариев,
но не отвечают на вопрос, как поведёт себя система
при отказах в реальных условиях эксплуатации:
с реальной нагрузкой, реальными сетевыми задержками
и реальным распределением запросов между репликами.
Этот пробел закрывается хаос-инжинирингом~---
методом, при котором в работающую систему намеренно вносятся
контролируемые сбои с целью проверки устойчивости.

Для системы ротации ключей хаос-эксперименты выполняются
средствами Chaos~Mesh~--- open-source-инструмента
для инъекции сбоев в Kubernetes-кластерах,
управляемого декларативно через CRD-описание эксперимента.
Инструмент поддерживает разные типы сбоев~--- \texttt{PodChaos}
(остановка pod-ов), \texttt{NetworkChaos} (сетевые задержки и разрывы),
\texttt{IOChaos}, \texttt{StressChaos} и другие~---
и два режима исполнения: разовый запуск
и периодический по расписанию.
Это позволяет одинаковыми средствами проводить как точечные
проверки конкретных архитектурных свойств,
так и непрерывную фоновую верификацию устойчивости.

Ниже рассматриваются два эксперимента,
проведённые для системы ротации ключей:
разовый~--- полный отказ распределённого кеша токенов
для оценки запаса прочности двухуровневой схемы кеширования
в клиентской библиотеке;
плановый~--- ежедневное нарушение сетевой связности pod-ов auth-jwt
в одной из зон доступности для непрерывной проверки устойчивости
к отказу целой зоны.

\textbf{Разовый эксперимент: отказ распределённого кеша.}
Кеш токенов в клиентской библиотеке Mindbox.Authentication
устроен как двухуровневый
(см.~\ref{subsec:buffer-time}):
локальный memory-кеш процесса
и общий распределённый кеш в виде кластера Dragonfly DB
в namespace \texttt{auth-jwt}, разделяемый всеми репликами потребителя.
Запрос за токеном сначала идёт в локальную память,
при промахе~--- в распределённый кеш,
и только при отсутствии и там~--- к auth-jwt за новым токеном.
Эксперимент полностью отключает уровень распределённого кеша
на боевом контуре Sigma:
описание \texttt{PodChaos} с действием \texttt{pod-failure}
и режимом \texttt{all} применяется ко всем pod-ам,
помеченным меткой \texttt{app.kubernetes.io/name: dragonfly},
на пять минут (листинг~\ref{lst:chaos-mesh-config}).

\begin{lstlisting}[
  label={lst:chaos-mesh-config},
  caption={Описание эксперимента \texttt{PodChaos} в Chaos~Mesh для отказа всех pod-ов Dragonfly~DB}]
kind: PodChaos
apiVersion: chaos-mesh.org/v1alpha1
metadata:
  namespace: auth-jwt
  name: auth-jwt-dragonfly-pod-failure-5m-1
spec:
  selector:
    namespaces:
      - auth-jwt
    labelSelectors:
      app.kubernetes.io/name: dragonfly
  mode: all
  action: pod-failure
  duration: 5m
\end{lstlisting}

Поведение системы во время эксперимента приведено
на \firef{fig:cache-failure}.
В момент полного отказа распределённого кеша
99-й процентиль времени ответа сервиса вырос примерно вдвое~---
с порядка десяти до двадцати миллисекунд,
тогда как 95-й процентиль и медианное значение
остались на типовом уровне.
Такое распределение деградации объясняется устройством
двухуровневого кеша.
Запросы с горячими ключами~--- массовый клиентский трафик~---
обслуживаются локальным memory-кешем
и не зависят от состояния распределённого слоя,
что и обеспечивает стабильность p95 и p50.
Деградация затрагивает только хвост распределения~---
запросы редких клиентов, для которых токен в локальной памяти
отсутствует и которые до отказа получали его из Dragonfly~DB.
В логах сервиса в это время фиксируются ошибки backend-операций
\texttt{HybridCache}, не приводящие к отказу в обслуживании.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/cache-failure.png}
  \caption{Время ответа сервиса при полном отказе распределённого кеша: рост p99 примерно вдвое при стабильных p95 и p50}
  \label{fig:cache-failure}
\end{figure}

Тем самым подтверждено, что полный отказ распределённого кеша
не приводит к деградации SLO и не вызывает срабатывания алертов:
ухудшение времени ответа происходит только на длинном хвосте
распределения, без отказа в обслуживании
и без влияния на основной поток трафика.
Клиентская библиотека сохраняет работоспособность
даже при выходе из строя целого уровня кеша
на боевом контуре с реальной нагрузкой.

\textbf{Плановый эксперимент: отказ зоны доступности.}
Чтобы устойчивость системы проверялась не только в момент релиза,
а на всём горизонте её жизни в production,
Chaos~Mesh используется и в режиме запусков по расписанию.
В этом режиме раз в сутки на боевом контуре выполняется
эксперимент типа \texttt{NetworkChaos},
нарушающий сетевую связность всех pod-ов auth-jwt в одной из зон
доступности кластера на ограниченное время.
Тем самым проверяется свойство более сильное, чем отказ одной реплики:
способность системы пережить выход из строя целой зоны доступности~---
стандартный сценарий сбоев в облачных
и собственных кластерных средах.

Корректное поведение системы в этом сценарии опирается
на два механизма, описанных в главе~\ref{ch3}:
повторных попыток (retry) клиентской библиотеки
при неудачном запросе токена и локального кеша токенов
с упреждающим обновлением, который позволяет работать
без обращений к auth-jwt в течение TTL-буфера.
Если оба механизма функционируют корректно,
отсутствие реплик auth-jwt в выбранной зоне не приводит
к отказу в обслуживании клиентов:
запросы перенаправляются на реплики в оставшихся зонах
после повторного обращения, либо обслуживаются
уже выпущенным в кеше токеном до его естественного обновления.

Критерий успешности~--- отсутствие алертов о деградации SLO
авторизации и отсутствие роста доли ошибок \texttt{5xx}
на стороне потребителей токенов за период эксперимента.
За всё время эксплуатации системы (см.~раздел~\ref{sec:ch4-rollout})
ни одного срабатывания алертов в ходе плановых хаос-экспериментов
зафиксировано не было, что подтверждает корректность реализации
механизмов отказоустойчивости.

\section{Апробация}\label{sec:ch4-rollout}

Система ротации ключей была введена в промышленную эксплуатацию
платформы Mindbox в марте 2026~года.
К моменту написания настоящей работы
она непрерывно функционирует на протяжении двух месяцев
и обслуживает все контуры платформы, описанные в~\ref{subsec:contours}:
от разработческой среды Alpha до боевых контуров Sigma и Gamma.

\subsection{Стратегия ввода ротации на контурах}\label{subsec:ch4-rollout-strategy}

Перевод каждого контура на автоматическую ротацию
проходил по фиксированному регламенту из трёх шагов:

\begin{enumerate}
  \item Все микросервисы контура переводились на новую систему
        авторизации, и ингресс контура начинал обслуживать запросы
        с использованием новой клиентской библиотеки.
  \item Ротация ключа запускалась вручную,
        после чего отслеживался фон ошибок (\texttt{4xx}/\texttt{5xx})
        на ингрессе контура.
        Если фон поднимался, выполнялся откат к предыдущему ключу
        в одно действие, проблема локализовывалась и исправлялась,
        после чего ротация запускалась повторно;
        итерации повторялись до тех пор,
        пока ручной запуск ротации не переставал давать прирост ошибок.
  \item Для контура включалась автоматическая ротация
        по расписанию.
\end{enumerate}

Скриншот фона ошибок на ингрессе во время одного
из ручных запусков ротации приведён на \firef{fig:rollout-errors}.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/rollout-errors.png}
  \caption{Фон ошибок на ингрессе контура во время ручного запуска ротации}
  \label{fig:rollout-errors}
\end{figure}

Порядок контуров выбирался по возрастанию рисков:

\begin{itemize}
  \item \textbf{Alpha}~--- контур разработчиков с собственным RSA-ключом
        и минимальной стоимостью ошибки;
        использовался для проверки самого регламента.
  \item \textbf{Infra}~--- внутренний инфраструктурный контур
        с ограниченным набором сервисов и потребителей;
        последствия возможной поломки локальны и не затрагивают клиентов.
  \item \textbf{Sigma}~--- самый новый и наиболее изолированный
        из боевых контуров;
        архитектура его сервисов ближе всего к актуальной,
        ингресс настроен прозрачно для наблюдения.
  \item \textbf{Omega}, развёрнутый в AWS, по архитектуре
        частично изолирован, но имеет иные средства наблюдения
        и более ограниченные доступы~---
        поэтому требует отдельного цикла проверки.
  \item \textbf{Gamma} и \textbf{Beta}~--- переводились в последнюю
        очередь: на них приходится основная нагрузка платформы
        и большинство легаси-сервисов,
        поэтому риск ошибки и её последствия максимальны.
\end{itemize}

\subsection{Автоматическая ротация по расписанию}\label{subsec:ch4-rollout-schedule}

После завершения раскатки автоматическая ротация ключей подписи
выполняется по расписанию на всех контурах
без участия инженеров эксплуатации.
Состояние процесса наблюдается через дашборд
с метрикой времени последней успешной ротации
для каждого ключа на каждом контуре
(\firef{fig:rotation-dashboard}).
Появление аномалии~--- увеличение интервала между ротациями
сверх ожидаемого~--- приводит к срабатыванию алерта
у дежурного инженера.

\subsection{Ограничения изоляции контуров Beta и Gamma}\label{subsec:ch4-rollout-isolation}

В ходе апробации не удалось в полном объёме достичь
требования изоляции контуров по ключу подписи,
сформулированного в~\ref{subsec:contour-isolation}.
Для контуров Alpha, Sigma и Omega задача решена:
auth-jwt каждого из них управляет собственным набором ключей,
а компрометация ключа на одном контуре не влияет на остальные.
Для контуров Beta и Gamma полного разделения добиться не удалось.
Причина~--- историческое сцепление этих контуров на уровне платформы:
часть микросервисов отсутствует на Beta,
и соответствующие запросы перенаправляются на Gamma
через межконтурный fallback-маршрут.
Разделение этой связки требует переноса и дублирования
части сервисов на Beta и оценивается платформенной командой Mindbox
примерно в один год работы;
выполнение этой работы выходит за рамки настоящего исследования.

До завершения соответствующих работ для пары Beta и Gamma
используется гибридная схема:
ротацией ключа подписи управляет auth-jwt контура Gamma,
а auth-jwt контура Beta читает актуальный закрытый RSA-ключ
из Vault Gamma по защищённому каналу.
Тем самым автоматическая ротация для Beta остаётся прозрачной
и не требует отдельного обслуживания,
однако полная криптографическая изоляция Beta и Gamma
по ключу подписи отложена до завершения переноса сервисов.
По сравнению с исходным состоянием системы,
в котором единый закрытый RSA-ключ был у всех боевых контуров
сразу (см.~\ref{subsec:jwt-scheme}),
текущая модель сокращает зону компрометации с пяти контуров
до пары Beta--Gamma и переводит её обновление в автоматический режим.

Сама задача разделения Beta и Gamma имеет
наблюдаемый критерий завершения.
Непреднамеренные межконтурные обращения~---
ситуации, когда запрос, авторизованный токеном с эмитентом одного контура,
попадает в обработчик на другом контуре~---
выявляются метрикой \texttt{CDP Contour Mismatch},
поднятой в рамках работ по наблюдаемости (см.~\ref{sec:observability}).
Метрика учитывает по парам \emph{эмитент токена}~$\to$\emph{namespace обработчика}
количество запросов, в которых контур эмитента не совпадает
с контуром обработчика.
На эту же метрику опирался запуск автоматической ротации:
устойчивое нулевое значение по всем парам служило критерием того,
что ротация ключа на Gamma не нарушит работу сервисов,
ошибочно получающих токены с других контуров.
Текущее состояние метрики приведено на \firef{fig:contour-mismatch}:
отдельные всплески непродолжительны
и значения сходятся к нулю на отрезках наблюдения.
Та же метрика будет служить индикатором готовности
к завершающему этапу~--- разделению Beta и Gamma по собственному ключу
после переноса соответствующих сервисов:
устойчивый ноль на длительном окне означает,
что межконтурное сцепление ликвидировано
и гибридную схему чтения ключа из Vault Gamma
можно безопасно отключить.

  \caption{Метрика \texttt{CDP Contour Mismatch}: межконтурные обращения по парам эмитент~--- namespace обработчика}
  \label{fig:contour-mismatch}
\end{figure}

\subsection{Эксплуатационные показатели}\label{subsec:ch4-rollout-metrics}

За период промышленной эксплуатации
зафиксировано следующее.
Все запланированные ротации завершились успешно.
Инцидентов авторизации, связанных с работой системы ротации
или с обновлением ключей подписи, не зарегистрировано.
Метрики времени ответа auth-jwt в моменты ротации
не отклонялись от типовых значений, приводимых ниже.
Ежедневные хаос-эксперименты, описанные
в разделе~\ref{sec:ch4-chaos},
не приводили к срабатыванию алертов о деградации авторизации.

Эксплуатационные показатели auth-jwt на контуре Gamma
за характерное окно наблюдения приведены на
\firef{fig:gamma-usage}.
Совокупный RPS не превышает примерно 150 запросов в секунду
при основном трафике на эндпоинт \texttt{Token/SyncTokenSet}
(оператор), а время ответа сервиса распределяется как
$p_{50}=5$~мс, $p_{95}=8$~мс, $p_{99}=13$~мс
при средней около $4{,}5$~мс.
Эпизодические пики $p_{99}$ до 14--15~мс с периодичностью
около двух часов наблюдаются стабильно
и не приводят к нарушению SLO в 30~мс
ни на одном из перцентилей.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/gamma-usage.png}
  \caption{Промышленные показатели auth-jwt на контуре Gamma: время ответа по перцентилям и распределение запросов по эндпоинтам}
  \label{fig:gamma-usage}
\end{figure}

Низкая нагрузка на auth-jwt в условиях,
когда платформа в целом обрабатывает свыше двух миллионов запросов
в минуту~\cite{MindboxResults2022},
объясняется работой клиентского кеша библиотеки Mindbox.Authentication
с упреждающим обновлением токенов (см.~\ref{subsec:buffer-time}).
Эффективность кеша иллюстрируется на \firef{fig:clients-cache}
дашбордом одного из наиболее нагруженных
семейств сервисов платформы~--- сервисов рекомендаций.
На этих сервисах частота попаданий в кеш (\emph{Cache~Hits})
держится на уровне $45\text{--}50$~тыс. в секунду,
тогда как частота промахов (\emph{Cache~Misses})~---
лишь несколько сотен в секунду.
Доля запросов авторизации,
требующих обращения к auth-jwt,
тем самым составляет порядка одного процента;
остальные обслуживаются токеном, уже находящимся в локальном кеше
библиотеки.
В масштабе всей платформы абсолютная частота операций авторизации
ещё выше~--- запросы к auth-jwt идут от всех микросервисов одновременно~---
однако сохраняющееся соотношение попаданий и промахов
обеспечивает, что доля трафика, доходящего до auth-jwt,
остаётся на уровне единиц процентов от общего объёма авторизаций.
Тем самым в промышленной эксплуатации подтверждается
ключевое архитектурное решение системы~---
снижение нагрузки на центральный сервис авторизации
за счёт переноса логики обновления токена на клиента.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/clients-cache.png}
  \caption{Эффективность кеша клиентской библиотеки в промышленной среде}
  \label{fig:clients-cache}
\end{figure}

Архитектура auth-jwt намеренно сделана stateless~---
всё разделяемое состояние выносится в PostgreSQL и Vault,~---
что позволяет масштабировать сервис горизонтально
добавлением реплик без изменения кода
или конфигурации остальных компонентов.
В Kubernetes-кластерах платформы для этого задействован
\emph{Horizontal Pod Autoscaler} (HPA),
который автоматически меняет число реплик auth-jwt
в зависимости от текущего потребления ресурсов.
При наблюдаемой нагрузке порядка 150~RPS на контур HPA удерживает
минимальное число реплик; вычислительные мощности,
не востребованные текущим трафиком, просто не выделяются.
При росте нагрузки те же реплики автоматически добавляются
без вмешательства инженеров.
Нагрузочное тестирование (см.~\ref{sec:ch4-load})
показывает верхнюю границу: один контур способен принять
не менее 15\,000~RPS~--- запас, более чем на два порядка
превышающий промышленный трафик.

\subsection{Апробация на научной конференции}\label{subsec:ch4-conference}

Дополнительно к промышленной апробации результаты работы
были представлены на научно-практической конкурс-конференции
студентов, аспирантов и молодых учёных
«Современные технологии в теории и практике
программирования»~\cite{SPbPUConference2026},
проведённой Высшей школой программной инженерии СПбПУ
при поддержке компании YADRO 22--23 апреля 2026 года.
Доклад был представлен в секции
«Прикладная программная инженерия: продукты, сервисы и системы».
По итогам секции работа заняла второе место,
что по регламенту конференции соответствует
победителю секции.

Положительная оценка предложенного решения членами жюри
подтверждает актуальность поставленной задачи
и новизну предложенного решения,
не имеющего готового аналога среди существующих open-source-систем
управления идентификацией (см.~\ref{sec:idp-analysis}).
Тем самым кроме промышленной верификации
результаты работы прошли и независимую оценку
внешним научно-практическим сообществом.

Полученные результаты подтверждают исходную гипотезу,
сформулированную во введении:
автоматическая плановая ротация криптографических ключей подписи
в платформе Mindbox достижима без прерывания работы сервисов
и без деградации производительности.
Тем самым выполнены задачи~5 (перевод микросервисов
на новую систему авторизации) и~6 (запуск автоматической ротации
по расписанию), поставленные во введении.

\section{Выводы по главе}\label{sec:ch4-conclusion}

В главе рассмотрена стратегия тестирования и приведены результаты
апробации системы ротации ключей в промышленной эксплуатации.
Каждый из четырёх компонентов системы покрыт типом тестов,
соответствующим его природе:
auth-jwt и клиентская библиотека~--- интеграционными тестами
с реальными зависимостями,
Kubernetes-оператор~--- E2E-тестами на встроенном кластере Kind,
Terraform-провайдер~--- юнит-тестами маппинга, валидаторов
и HTTP-клиента к auth-jwt.
Прогон всех тестов вместе с проверкой секретов и ИИ-ревью кода
является обязательным условием приёмки изменений в GitLab~CI.
Помимо функционального тестирования
auth-jwt подвергается нагрузочному тестированию
и непрерывному хаос-инжинирингу в промышленной среде.
