\chapter{Тестирование и апробация}\label{ch4}

Данная глава посвящена тестированию компонентов системы,
разработанных в главе~\ref{ch3},
и апробации системы в промышленной среде.
Сначала обозначается общая стратегия тестирования
и устройство конвейера непрерывной интеграции.
Затем последовательно рассматриваются тесты каждого
из четырёх компонентов системы:
auth-jwt, Kubernetes-оператора, Terraform-провайдера
и клиентской библиотеки.
Далее приводятся результаты нагрузочного тестирования auth-jwt
и описывается хаос-инжиниринг в промышленной среде.
В заключение приводится результат апробации
после внедрения системы в эксплуатацию.

\section{Стратегия тестирования}\label{sec:ch4-strategy}

Компоненты системы существенно различаются по составу кода
и характеру связей с инфраструктурой, поэтому каждый из них
тестируется отдельным способом~--- единого подхода,
одинаково эффективного для всех, не существует.

Классическая пирамида тестов~\cite{Cohn2009}
предписывает массовое использование юнит-тестов в основании,
меньшее количество интеграционных в середине
и небольшое число сквозных тестов на вершине.
Такое распределение оптимизирует время прогона:
юнит-тесты исполняются за миллисекунды,
тогда как сквозные~--- за секунды или минуты.
Однако пирамида плохо подходит для инфраструктурного кода.
Существенная часть логики auth-jwt и оператора~---
это связующий код между внешними системами:
PostgreSQL, HashiCorp Vault, Kubernetes API.
Юнит-тестирование такого кода требует мокирования внешних систем,
а моки воспроизводят лишь предположения разработчика о поведении
зависимости, а не само поведение.
Эмпирическое исследование~\cite{InozemtsevaHolmes2014}
показывает, что покрытие кода тестами слабо коррелирует
со способностью набора тестов обнаруживать реальные дефекты:
важнее не доля юнит-тестов, а соответствие тестов
наблюдаемому поведению системы.

С учётом сказанного для auth-jwt и клиентской библиотеки
основная масса тестов~--- интеграционные:
auth-jwt тестируется с реальными PostgreSQL и Vault,
поднятыми через Testcontainers~\cite{Testcontainers};
клиентская библиотека~--- с реальным экземпляром ASP.NET~Core
через \texttt{WebApplicationFactory}~\cite{TestWebApplicationFactory}.
Для Kubernetes-оператора применяется сквозное тестирование
на встроенном в контейнер кластере Kind~\cite{Kind}
с программной заглушкой auth-jwt:
юнит-тесты здесь дают слабые гарантии из-за плотного взаимодействия
оператора с Kubernetes API.
Для Terraform-провайдера достаточно юнит-тестирования
схемы и преобразований: HTTP-контракт,
на котором держится его взаимодействие с auth-jwt,
проверяется интеграционными тестами auth-jwt
со стороны сервера.

\subsection{Микросервис auth-jwt}\label{subsec:ch4-auth-jwt-tests}

Для интеграционного тестирования auth-jwt разработан
предметно-ориентированный язык, описывающий сценарии тестов
на уровне понятий предметной области.
Применение предметно-ориентированных языков повышает выразительность
и читаемость кода в узких задачах за счёт ограничения общности
синтаксиса и операций~\cite{Mernik2005DSL}.
Разработанный язык состоит из трёх слоёв:
прямые операции с базой данных,
операции через HTTP API
и операции с секретами в Vault.

На \firef{fig:integration-test} приведён
пример теста генерации токена.

\begin{codeblock}
\begin{lstlisting}[language={[Sharp]C}]
[TestMethod]
public async Task GenerateToken_ValidParameters_TokenGenerated()
{
    // Arrange: создание клиента через DSL
    var client = BuildAuthClient(TestClientId,
        tokenPolicies: [BuildPolicy(TestPolicy,
            permissions: ["ReadSomething"],
            allowTenantHeader: true)]);
    await AuthClientsDb.CreateAsync(client);
    var k8sToken = GetK8STokenFake(TestClientId);

    // Act: запрос токена через HTTP
    using var content = JsonContent.Create(
        new ClientTokenRequest {
            ClientId = TestClientId,
            Tenant = "testTenant",
            Policy = TestPolicy });
    var response = await ServicesProject.SendAsync<TokenResponse>(
        "/token", HttpMethod.Post, content, token: k8sToken);

    // Assert: проверка claims и метрик
    var jwt = ReadJsonWebToken(response.Token);
    Assert.AreEqual(TestClientId, jwt.Subject);
    AssertClaim(jwt, MindboxJwtConstants.TenantClaim, "testTenant");

    var metricValue = _tokenIssuedCounter
        .WithLabels(TestClientId, TestPolicy, "testTenant").Value;
    Assert.AreEqual(1, metricValue);
}
\end{lstlisting}
\codefig{Интеграционный тест генерации токена с использованием DSL}{fig:integration-test}
\end{codeblock}

Тест читается как спецификация:
создать клиента с политикой,
запросить токен,
проверить содержимое токена и инкремент соответствующей метрики.
Вспомогательные методы \texttt{BuildAuthClient},
\texttt{BuildPolicy}, \texttt{GetK8STokenFake}
скрывают подготовку инфраструктуры,
а \texttt{AssertClaim}~--- типовые проверки полей JWT.

\subsection{Kubernetes-оператор}\label{subsec:ch4-operator-tests}

В отличие от auth-jwt, основная часть кода оператора
описывает взаимодействие с Kubernetes API,
поэтому изолированные юнит-тесты дают слабые гарантии:
поведение, заложенное в моки API, может расходиться
с реальным поведением кластера.
По этой причине оператор проверяется сквозными тестами
на встроенном в контейнер кластере Kind~\cite{Kind}.
Тесты пишутся на Ginkgo~\cite{Ginkgo}~---
BDD-ориентированном фреймворке для языка Go.
Перед прогоном каждого сценария разворачивается локальный
кластер Kind и в нём поднимается оператор вместе
с программной заглушкой auth-jwt,
что позволяет наблюдать реальное поведение реконсиляции
без необходимости в работающем экземпляре микросервиса.

На \firef{fig:e2e-test} приведён сокращённый сценарий,
проверяющий механизм надёжного удаления токенов.
Если разработчик убирает определение токена
из спецификации Custom Resource,
оператор намеренно не удаляет соответствующую запись
из Kubernetes Secret до истечения её срока действия:
такая отсрочка даёт время восстановить случайно удалённую
конфигурацию без нарушения работы потребителей.

\begin{codeblock}
\begin{lstlisting}[language=Go]
It("deleting tokens from CR does not remove from secret "+
    "until expiration", func() {

    By("applying valid AuthJwtConfig")
    cmd.ApplyAuthJwtConfig(authjwtv1.AuthJwtConfig{
        Spec: authjwtv1.AuthJwtConfigSpec{
            Contour:    "stable",
            SecretName: secretName,
            Tokens: []authjwtv1.TokenSpec{{
                Name:   "api-token",
                Policy: authjwt.FakeShortLivedPolicy,
            }},
        },
    })

    By("awaiting first reconcile")
    waitForFirstReconcile(clientNS, clientName)

    By("removing tokens from spec")
    cmd.ApplyAuthJwtConfig(authjwtv1.AuthJwtConfig{
        Spec: authjwtv1.AuthJwtConfigSpec{
            Contour: "stable", SecretName: secretName,
            Tokens:  []authjwtv1.TokenSpec{},
        },
    })

    By("checking token remains in secret")
    Consistently(func(g Gomega) {
        secret, _ := cmd.GetAuthSecretData(clientNS, secretName)
        g.Expect(secret.Tokens).To(HaveKey("api-token"))
    }, 2*time.Second, 200*time.Millisecond).Should(Succeed())

    By("waiting for secret removal after expiration")
    Eventually(func(g Gomega) {
        secret, _ := cmd.GetAuthSecretData(clientNS, secretName)
        g.Expect(secret.Tokens).NotTo(HaveKey("api-token"))
    }).Should(Succeed())
})
\end{lstlisting}
\codefig{Сквозной тест: токен остаётся в Secret после удаления из спецификации до истечения срока действия}{fig:e2e-test}
\end{codeblock}

Тест использует две ключевые конструкции Ginkgo:
\texttt{Consistently}~--- утверждает, что условие выполняется
непрерывно в течение заданного интервала;
\texttt{Eventually}~--- ожидает выполнения условия с таймаутом.

\subsection{Terraform-провайдер}\label{subsec:ch4-terraform-tests}

Поскольку провайдер не содержит независимой бизнес-логики
(см.~\ref{sec:terraform-impl})
и работает как тонкий слой между конфигурацией пользователя
и HTTP API auth-jwt, основная часть его юнит-тестов
проверяет преобразование данных между внутренним представлением
Terraform и форматом HTTP-запросов.
Чистые функции маппинга и кастомные валидаторы схемы
тестируются изолированно, а HTTP-клиент к auth-jwt~---
с помощью \texttt{httptest.Server}~\cite{GoHttptest},
встроенного в стандартную библиотеку Go средства
для запуска тестового HTTP-сервера в том же процессе, что и тест.
Пример юнит-теста маппинга API-ответа в состояние ресурса
приведён на \firef{fig:tf-map-test}.

\begin{codeblock}
\begin{lstlisting}[language=Go]
state, diags := mapApiResponseToState(&AuthClientResponse{
    ClientID:          "client-a",
    AllowCustomClaims: true,
    EnforcedClaims:    map[string][]string{"iss": {"issuer-a"}},
    TokenPolicies: map[string]TokenPolicyDto{
        "default": {TTLSeconds: 3600,
                    Permissions: []string{"read", "write"}},
    },
})
if diags.HasError() { t.Fatalf("unexpected: %v", diags) }
if state.ClientID.ValueString() != "client-a" { t.Fatal() }
if state.TokenPolicies["default"].TTLSeconds.ValueInt32() != 3600 {
    t.Fatal()
}
\end{lstlisting}
\codefig{Юнит-тест маппинга API-ответа в состояние ресурса}{fig:tf-map-test}
\end{codeblock}

В приведённом тесте функция \texttt{mapApiResponseToState}
принимает ответ от auth-jwt в виде структуры \texttt{AuthClientResponse}
и возвращает соответствующее ему состояние ресурса Terraform.
Проверяется, что преобразование выполнено без ошибок диагностики
и что значения отдельных полей в полученном состоянии совпадают
с ожидаемыми. Аналогичным образом покрываются обратное преобразование
плана пользователя в запрос к API и валидаторы зависимостей
между блоками конфигурации.

Полноценные приёмочные тесты~--- сценарии \texttt{terraform~apply}
против реального экземпляра auth-jwt~--- в провайдере не запускаются.
HTTP-контракт, на котором держится взаимодействие провайдера
с auth-jwt, проверен интеграционными тестами auth-jwt
со стороны сервера (см.~\ref{subsec:ch4-auth-jwt-tests}),
поэтому юнит-тестов маппинга, валидаторов схемы
и HTTP-клиента провайдера достаточно для практической уверенности
в его корректности.

\subsection{Клиентская библиотека Mindbox.Authentication}\label{subsec:ch4-lib-tests}

Библиотека Mindbox.Authentication (см.~\ref{sec:client-lib-impl})
покрыта двумя уровнями тестов.
Юнит-тесты проверяют изолированные компоненты:
кеш, вычисление TTL-буфера, построение ключа,
политики авторизации, конфигурирование.
Интеграционные тесты запускают полноценный экземпляр ASP.NET~Core
через \texttt{WebApplicationFactory}~\cite{TestWebApplicationFactory}
и проверяют сценарии полного цикла авторизации:
обработку валидного токена, отклонение просроченного,
проверку разрешений и работу API-ключей.

Пример интеграционного теста, проверяющего, что запрос
к защищённому эндпоинту с валидным токеном возвращает успешный ответ,
приведён на \firef{fig:lib-integration-test}.

\begin{codeblock}
\begin{lstlisting}[language={[Sharp]C}]
[TestMethod]
public async Task ProtectedEndpoint_WithValidToken_Returns200()
{
    await using var factory = new TestWebApplicationFactory();
    var token = await factory.IssueTokenAsync(
        clientId: TestClientId,
        policy: ReadOrdersPolicy);

    using var client = factory.CreateClient();
    client.DefaultRequestHeaders.Authorization =
        new AuthenticationHeaderValue("Bearer", token);

    var response = await client.GetAsync("/orders");

    Assert.AreEqual(HttpStatusCode.OK, response.StatusCode);
}
\end{lstlisting}
\codefig{Интеграционный тест клиентской библиотеки: авторизация валидным токеном}{fig:lib-integration-test}
\end{codeblock}

Тест поднимает экземпляр приложения с подключённой библиотекой
Mindbox.Authentication, выпускает тестовый токен через предусмотренный
для этого вспомогательный метод фабрики, прикладывает токен
к запросу и проверяет, что защищённый эндпоинт отвечает кодом~200.
Аналогичным образом тестируются отклонение просроченного токена,
проверка отсутствия требуемого разрешения и обслуживание запроса
API-ключом вместо JWT.
Полный набор юнит-тестов класса \texttt{CachedAuthJwtClient},
отвечающего за кеширование токенов в библиотеке,
приведён в приложении~\ref{app:source-code}

\section{Нагрузочное тестирование auth-jwt}\label{sec:ch4-load}

Нагрузочное тестирование проводится для auth-jwt~---
единственного компонента системы, синхронно обрабатывающего
каждый внешний запрос на получение токена авторизации.
Цель~--- оценить запас по SLO на генерацию токена
(не более 30~мс по 95-му процентилю).

Инструментом выбран Grafana~k6~\cite{GrafanaK6}~---
фреймворк нагрузочного тестирования с открытым исходным кодом,
со сценариями на JavaScript и нативным экспортом метрик в Prometheus.
Преимущество k6~--- единая модель сценариев, генераторов нагрузки
и отчётности, без отдельного агрегатора и сбора результатов вручную.
Тестирование проводится последовательно в двух средах.
Сначала прогон выполняется на контуре Alpha,
где допустимо безопасно достигать предельных значений RPS
без риска для пользователей.
После подтверждения результатов на Alpha
прогон повторяется на промышленном контуре Gamma,
что позволяет верифицировать запас производительности
в реальной кластерной инфраструктуре.
На обоих стендах auth-jwt работает с реальными PostgreSQL и Vault~---
без подмены зависимостей программными заглушками.
Сценарий имитирует штатный путь авторизации запросов:
запрос токена через \texttt{POST /token}
с уже зарегистрированным клиентом и прогретым кешем подписи.

Целевой график нагрузки~--- линейный рост RPS до точки,
в которой либо нарушается SLO,
либо инструмент перестаёт выдавать заданную частоту запросов.
В проведённых прогонах генератор достиг 15~000~RPS,
после чего пиковая нагрузка упёрлась в производительность самого k6;
auth-jwt продолжал отвечать без отказов.
На пике 95-й процентиль времени ответа составил 80~мс,
что выше SLO 30~мс, но соответствует нагрузке,
существенно превосходящей промышленную (см.~ниже).
Точка деградации auth-jwt~--- значение RPS,
при котором сервис теряет способность держать SLO~---
в эксперименте не достигнута.
График зависимости времени ответа от подаваемой нагрузки
приведён на \firef{fig:k6-load}.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/k6-load.png}
  \caption{Нагрузочное тестирование auth-jwt в Grafana k6: RPS и время ответа}

Результаты нагрузочного тестирования следует сопоставлять
с реальной нагрузкой контуров платформы.
На контуре Gamma~--- максимальном по входящему трафику~---
наблюдаемая нагрузка на auth-jwt не превышает примерно 150~RPS,
а 95-й процентиль времени ответа держится на уровне 8~мс
(детально показатели промышленной эксплуатации
приводятся в~\ref{sec:ch4-rollout}, \firef{fig:gamma-usage}).
Низкая нагрузка на auth-jwt относительно числа обрабатываемых
платформой запросов~--- прямое следствие архитектурных решений
главы~\ref{ch3}: упреждающего кеширования токенов в клиентской
библиотеке и пакетной доставки через оператор.
Сводное сопоставление приведено в \taref{tab:ch4-load-comparison}.

(8~мс по факту против допустимых 30~мс).
Во-вторых, кратное увеличение нагрузки до уровня,
в сто раз превышающего наблюдаемый промышленный пик,
не выводит auth-jwt из строя~---
сервис продолжает отвечать в пределах десятков миллисекунд,
а нарушение SLO в пиковом сценарии нагрузочного теста
не означает деградации в производственной эксплуатации.
Из обнаруженного разрыва между промышленной нагрузкой
и пропускной способностью сервиса вытекает практическое следствие
для размера выделяемых auth-jwt ресурсов, которое рассматривается
в~\ref{sec:ch4-rollout}.

\section{Хаос-инжиниринг в промышленной среде}\label{sec:ch4-chaos}

Автоматизированные тесты в CI проверяют корректность системы
относительно зафиксированного набора сценариев,
но не отвечают на вопрос, как поведёт себя система
при отказах в условиях промышленной эксплуатации~---
при фактической нагрузке, сетевых задержках и распределении
запросов между репликами.
Этот пробел закрывается хаос-инжинирингом~---
методом, при котором в работающую систему намеренно вносятся
контролируемые сбои с целью проверки устойчивости.

Для системы ротации ключей хаос-эксперименты выполняются
средствами Chaos~Mesh~\cite{ChaosMesh}~---
инструмента для инъекции сбоев в Kubernetes-кластерах
с открытым исходным кодом,
управляемого декларативно через манифест,
описывающий тип сбоя, объект воздействия и продолжительность.
Поддерживаются основные виды сбоев,
встречающиеся в эксплуатации:
остановка подов, сетевые задержки и разрывы соединений,
сбои операций ввода-вывода, перегрузка процессора и памяти.
Инструмент позволяет запускать эксперимент как разово,
так и по расписанию,
что даёт возможность одинаковыми средствами
проводить точечные проверки конкретных архитектурных свойств
и непрерывную фоновую верификацию устойчивости.

Ниже рассматриваются два эксперимента,
проведённые для системы ротации ключей:
разовый~--- полный отказ распределённого кеша токенов
для оценки изменения нагрузки на auth-jwt
и поведения сервиса в этих условиях;
плановый~--- ежедневное нарушение сетевой связности подов auth-jwt
в одной из зон доступности кластера для непрерывной проверки
устойчивости к отказу целой зоны.

\subsection{Разовый эксперимент: отказ распределённого кеша}\label{subsec:ch4-chaos-cache}

Цель эксперимента~--- проверить поведение auth-jwt
при полном отказе распределённого кеша токенов:
сохранит ли сервис работоспособность,
не возникнет ли длительных ответов из-за неверно
настроенных таймаутов и не выйдет ли время ответа за SLO.

Эксперимент проводится на промышленном контуре Sigma.
Манифест эксперимента (\firef{fig:chaos-mesh-config})
объявляет одновременный сбой всех экземпляров распределённого
кеша на пять минут.

\begin{codeblock}
\begin{lstlisting}[]
kind: PodChaos
apiVersion: chaos-mesh.org/v1alpha1
metadata:
  namespace: auth-jwt
  name: auth-jwt-dragonfly-pod-failure-5m-1
spec:
  selector:
    namespaces:
      - auth-jwt
    labelSelectors:
      app.kubernetes.io/name: dragonfly
  mode: all
  action: pod-failure
  duration: 5m
\end{lstlisting}
\codefig{Манифест эксперимента в Chaos~Mesh: одновременный сбой всех экземпляров распределённого кеша на пять минут}{fig:chaos-mesh-config}
\end{codeblock}

Поведение auth-jwt во время эксперимента приведено
на \firef{fig:cache-failure}.
В момент полного отказа распределённого кеша
99-й процентиль времени ответа сервиса вырос примерно вдвое~---
с порядка десяти до двадцати миллисекунд,
тогда как 95-й процентиль и медианное значение
остались на типовом уровне.
Основной поток запросов был обработан без замедления;
деградация коснулась только хвоста распределения,
и нарушения SLO 30~мс не зафиксировано ни на одном из перцентилей.
В логах в это время фиксируются ошибки операций
распределённого уровня кеша через библиотеку
\texttt{HybridCache}~\cite{HybridCache},
не приводящие к отказу в обслуживании.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/cache-failure.png}
  \caption{Время ответа auth-jwt при полном отказе распределённого кеша: рост p99 примерно вдвое при стабильных p95 и p50}
  \label{fig:cache-failure}
\end{figure}

Тем самым подтверждено, что полный отказ распределённого кеша
не выводит auth-jwt из границ SLO и не вызывает срабатывания
алертов: ухудшение времени ответа происходит только
на длинном хвосте распределения, без отказа в обслуживании
и без влияния на основной поток трафика.
Сервис сохраняет работоспособность при выходе из строя
распределённого кеша на промышленном контуре с реальной нагрузкой.

\subsection{Плановый эксперимент: отказ зоны доступности}\label{subsec:ch4-chaos-az}

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/zone-chaos-test.png}
  \caption{Логи auth-jwt в окне планового хаос-эксперимента: с момента начала до окончания инъекции сетевого сбоя в зоне доступности}
  \label{fig:zone-chaos}
\end{figure}

Чтобы устойчивость системы проверялась не только в момент релиза,
а на всём горизонте её жизни в эксплуатации,
Chaos~Mesh используется и в режиме запусков по расписанию.
В этом режиме раз в сутки на промышленном контуре выполняется
сетевой хаос-эксперимент, нарушающий сетевую связность всех подов
auth-jwt в одной из зон доступности
кластера~\cite{YandexCloudZones} на ограниченное время.
Тем самым проверяется свойство более сильное, чем отказ одной реплики:
способность системы пережить выход из строя целой зоны доступности~---
стандартный сценарий сбоев в облачных
и собственных кластерных средах.

Устойчивость в этом сценарии обеспечивают два механизма,
описанных в главе~\ref{ch3}:
повторные попытки запроса токена в клиентской библиотеке
с экспоненциальным наращиванием интервала между
попытками~\cite{AWSExponentialBackoff}
и локальный кеш токенов с упреждающим обновлением,
позволяющий обслуживать запросы из уже выпущенных токенов
без обращения к auth-jwt.
В сочетании эти механизмы приводят к тому, что недоступность
реплик в выбранной зоне не вызывает отказа в обслуживании:
запросы либо перенаправляются на реплики в оставшихся зонах
после повторной попытки, либо обслуживаются токеном из кеша.

Критерий успешности~--- отсутствие алертов о деградации SLO
авторизации и отсутствие роста доли необработанных ошибок
на стороне потребителей токенов за период эксперимента.
В период эксплуатации (см.~\ref{sec:ch4-rollout})
плановые хаос-эксперименты к срабатыванию алертов не приводят.
На этапе разработки ситуация была другой:
часть прогонов выявляла рост ошибок у потребителей,
что и послужило основанием для добавления
экспоненциальной задержки повторных попыток
в клиентскую библиотеку и в Kubernetes-оператор.
После этой доработки регулярные прогоны на промышленных контурах
проходят без срабатывания алертов,
что подтверждает корректность реализованных механизмов
отказоустойчивости.
Пример логов сервиса в окне планового эксперимента,
взятый из системы наблюдаемости, приведён на \firef{fig:zone-chaos}.

\section{Апробация}\label{sec:ch4-rollout}

Система ротации ключей была введена в промышленную эксплуатацию
платформы Mindbox 30~марта 2026~года.
К моменту написания настоящей работы
она непрерывно функционирует на протяжении двух месяцев
и обслуживает все контуры платформы, описанные в~\ref{subsec:contours}:
от разработческой среды Alpha до промышленных контуров Sigma и Gamma.

\subsection{Стратегия ввода ротации на контурах}\label{subsec:ch4-rollout-strategy}

Запуску автоматической ротации предшествовала четырёхмесячная
работа платформенной команды по адаптации всех микросервисов
платформы к новой системе авторизации.
До завершения этого этапа ротация не могла быть включена ни на одном
из контуров: часть сервисов продолжала использовать предыдущую
схему авторизации и не получила бы обновлённый ключ подписи.

После завершения миграции для каждого контура применялся
фиксированный регламент из трёх шагов:

\begin{enumerate}
  \item Ротация ключа запускалась вручную,
        после чего отслеживалось количество отказов в проверке
        подписи токена у потребителей и необработанных ошибок
        на стороне auth-jwt.
  \item Если эти показатели росли, выполнялся откат к предыдущему
        ключу в одно действие, проблема локализовывалась
        и исправлялась, после чего ротация запускалась повторно;
        итерации повторялись до тех пор, пока ручной запуск ротации
        не переставал давать прирост ошибок.
  \item Для контура включалась автоматическая ротация
        по расписанию.
\end{enumerate}

Скриншот соответствующих метрик во время одного из ручных запусков
ротации приведён на \firef{fig:rollout-errors}.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/rollout-errors.png}
  \caption{Фон ошибок авторизации во время ручного запуска ротации}
  \label{fig:rollout-errors}
\end{figure}

Порядок контуров выбирался по возрастанию рисков
(назначение контуров см.~в~\ref{subsec:contours}):

\begin{itemize}
  \item \emph{Alpha}~--- свой RSA-ключ и минимальная стоимость
        ошибки; использовался для отладки самого регламента.
  \item \emph{Infra}~--- ограниченный круг потребителей;
        последствия возможной поломки локальны.
  \item \emph{Sigma}~--- наиболее изолированный из промышленных контуров,
        прозрачная наблюдаемость.
  \item \emph{Omega} (AWS)~--- иные средства наблюдения
        и более ограниченные доступы;
        требует отдельного цикла проверки.
  \item \emph{Gamma} и \emph{Beta}~--- основная нагрузка платформы
        и наиболее тесно связанные между собой контуры
        (см.~\ref{sec:exchange}),
        разделить которые по ключу подписи труднее всего;
        риск ошибки и её последствия максимальны.
\end{itemize}

\subsection{Автоматическая ротация по расписанию}\label{subsec:ch4-rollout-schedule}

После завершения раскатки автоматическая ротация ключей подписи
выполняется по расписанию на всех контурах
без участия инженеров эксплуатации.
Состояние процесса наблюдается через дашборд
с метрикой времени последней успешной ротации
для каждого ключа на каждом контуре
(\firef{fig:rotation-dashboard}).
Появление аномалии~--- увеличение интервала между ротациями
сверх ожидаемого~--- приводит к срабатыванию алерта
у дежурного инженера.

\subsection{Ограничения изоляции контуров Beta и Gamma}\label{subsec:ch4-rollout-isolation}

Полностью изолировать контуры Beta и Gamma по ключу подписи
(см.~\ref{subsec:contour-isolation}) в рамках апробации не удалось
из-за исторически сильной связности этих контуров на уровне платформы
(см.~\ref{sec:exchange}).
До завершения их разделения для пары Beta--Gamma используется
гибридная схема: Gamma выступает активным контуром
и управляет ротацией ключа подписи,
а Beta~--- пассивным, читая актуальный закрытый RSA-ключ
из Vault Gamma по защищённому каналу.
Для контролируемого снятия этой схемы поднята отдельная метрика
\texttt{Contour Mismatch} (см.~\ref{sec:observability}),
выявляющая запросы, в которых контур эмитента токена
не совпадает с контуром обработчика;
текущее её состояние приведено на \firef{fig:contour-mismatch}.
Платформенная команда Mindbox в течение примерно года
ведёт работу по полному разделению контуров;
по её завершении, при устойчивом нулевом значении метрики,
гибридная схема будет отключена, а у Beta появится
собственный ключ подписи.

\subsection{Эксплуатационные показатели}\label{subsec:ch4-rollout-metrics}

За период промышленной эксплуатации
зафиксировано следующее.
Все запланированные ротации завершились успешно.
Инцидентов авторизации, связанных с работой системы ротации
или с обновлением ключей подписи, не зарегистрировано.
Метрики времени ответа auth-jwt в моменты ротации
не отклонялись от типовых значений, приводимых ниже.
Ежедневные хаос-эксперименты, описанные
в разделе~\ref{sec:ch4-chaos},
не приводили к срабатыванию алертов о деградации авторизации.

Эксплуатационные показатели auth-jwt на контуре Gamma
за характерное окно наблюдения приведены на
\firef{fig:gamma-usage}.
Совокупный RPS не превышает примерно 150 запросов в секунду,
а время ответа сервиса распределяется как
$p_{50}=5$~мс, $p_{95}=8$~мс, $p_{99}=13$~мс
при средней около $4{,}5$~мс.
Эпизодические пики $p_{99}$ до 14--15~мс с периодичностью
около двух часов наблюдаются стабильно
и не приводят к нарушению SLO в 30~мс
ни на одном из перцентилей.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/gamma-usage.png}
  \caption{Промышленные показатели auth-jwt на контуре Gamma: время ответа по перцентилям и распределение запросов по эндпоинтам}
  \label{fig:gamma-usage}
\end{figure}

Низкая нагрузка на auth-jwt в условиях,
когда платформа в целом обрабатывает свыше двух миллионов запросов
в минуту~\cite{MindboxResults2022},
объясняется работой клиентского кеша библиотеки Mindbox.Authentication
с упреждающим обновлением токенов (см.~\ref{subsec:buffer-time}).
Эффективность кеша иллюстрируется на \firef{fig:clients-cache}
дашбордом одного из наиболее нагруженных
семейств сервисов платформы~--- сервисов рекомендаций.
На этих сервисах частота попаданий в кеш (\emph{Cache~Hits})
держится на уровне $45\text{--}50$~тыс. в секунду,
тогда как частота промахов (\emph{Cache~Misses})~---
лишь несколько сотен в секунду.
Доля запросов авторизации,
требующих обращения к auth-jwt,
тем самым составляет порядка одного процента;
остальные обслуживаются токеном, уже находящимся в локальном кеше
библиотеки.
В масштабе всей платформы абсолютная частота получений токена
ещё выше~--- обращения идут от всех микросервисов одновременно,~---
однако сохраняющееся соотношение попаданий и промахов
обеспечивает, что доля трафика, доходящего до auth-jwt,
остаётся на уровне единиц процентов
от общего числа получений токена.
Ещё более существенно нагрузку на auth-jwt снижает
Kubernetes-оператор:
он централизованно выпускает токены пачками
и кладёт их в Kubernetes Secret потребителя,
поэтому большинству микросервисов не требуется обращаться
к auth-jwt самостоятельно~--- они получают актуальный токен
из локально смонтированного Secret.
В результате подтверждаются два ключевых архитектурных решения
системы: централизованная пакетная доставка токенов оператором
и упреждающее обновление в клиентской библиотеке.

\begin{figure}[h]
  \centering
  \includegraphics[width=\textwidth]{diagrams/img/clients-cache.png}
  \caption{Эффективность кеша клиентской библиотеки в промышленной среде}
  \label{fig:clients-cache}
\end{figure}

Stateless-архитектура auth-jwt (см.~\ref{sec:architecture})
позволяет масштабировать сервис горизонтально.
В Kubernetes-кластерах платформы для этого задействован
\emph{Horizontal Pod Autoscaler} (HPA)~\cite{KubernetesHPA},
который автоматически меняет число реплик auth-jwt
в зависимости от текущего потребления ресурсов.
При наблюдаемой нагрузке порядка 150~RPS на контур HPA удерживает
минимальное число реплик; вычислительные мощности,
не востребованные текущим трафиком, просто не выделяются.
При росте нагрузки те же реплики автоматически добавляются
без вмешательства инженеров.
Нагрузочное тестирование (см.~\ref{sec:ch4-load})
показывает верхнюю границу: один контур способен принять
не менее 15\,000~RPS~--- запас, более чем на два порядка
превышающий промышленный трафик.

По итогам секции работа заняла второе

Положительная оценка предложенного решения членами жюри

\section{Выводы по главе}\label{sec:ch4-conclusion}

В главе изложена стратегия тестирования системы ротации ключей
и приведены результаты её апробации в промышленной эксплуатации.
Сводные показатели по ключевым требованиям представлены
в \taref{tab:ch4-results}.

\begin{table}[ht!]
  \centering
  \caption{Сводные результаты тестирования и апробации}
  \label{tab:ch4-results}
  \begin{tabular}{p{6cm}p{5cm}p{4cm}}
    \hline
    \textbf{Требование} & \textbf{Критерий} & \textbf{Факт} \\

    SLO времени ответа auth-jwt & p95 $\leq 30$~мс & 8~мс (Gamma) \\

Содержательно полученные показатели интерпретируются следующим образом.
Заявленный SLO на генерацию токена~--- 30~мс по 95-му процентилю~---
в промышленной эксплуатации выдерживается с запасом почти в четыре
раза: фактическое значение p95 на максимальном по нагрузке контуре
Gamma составляет 8~мс (см.~\ref{subsec:ch4-rollout-metrics}).
Нагрузочное тестирование на стенде с реальными зависимостями
довело частоту запросов до 15\,000~RPS~--- это в сто раз больше
наблюдаемого промышленного пика;
сервис продолжал отвечать без отказов,
а сама точка деградации не была достигнута,
так как ограничение возникло уже на стороне генератора нагрузки.
Автоматическая ротация выполняется по расписанию на всех контурах
платформы непрерывно в течение двух месяцев и за это время
не потребовала вмешательства инженеров эксплуатации;
ни один инцидент авторизации, связанный с ротацией или
со сменой ключей подписи, не был зафиксирован
(см.~\ref{subsec:ch4-rollout-metrics}).
Устойчивость к отказам компонентов системы непрерывно проверяется
ежедневными хаос-экспериментами на промышленном контуре~---
ни одно срабатывание алертов SLO по результатам таких экспериментов
зафиксировано не было (см.~\ref{subsec:ch4-chaos-az}).

Полученные результаты подтверждают исходную гипотезу,
сформулированную во введении:
автоматическая плановая ротация криптографических ключей подписи
в платформе Mindbox достижима без прерывания работы сервисов
и без деградации производительности.
Тем самым в главе закрыты задачи тестирования компонентов системы
и запуска автоматической ротации ключей по расписанию,
поставленные во введении.
Полная криптографическая изоляция контуров Beta и Gamma
по ключу подписи в рамках работы не достигнута
по причинам, лежащим вне разрабатываемой системы~---
из-за исторического сцепления этих контуров на уровне платформы~---
и относится к работам платформенной команды Mindbox,
оценочно занимающим около года.
