\section{Текущее устройство микросервисной авторизации}\label{sec:current-auth}

\subsection{Микросервисная мультитенантная архитектура}\label{subsec:arch}

Платформа Mindbox представляет собой мультитенантную микросервисную систему,
насчитывающую порядка 120 независимо развёртываемых сервисов.
Клиентами (тенантами) платформы являются компании, использующие Mindbox
для автоматизации маркетинга и роста своего бизнеса, ~--- например, Яндекс Образование, Купер, СДЭК и другие.
Каждый сервис обслуживает запросы разных тенантов одновременно, разделяя данные на уровне приложения
за счет добавления идентификатора клиента в claim \texttt{tenant} JWT-токена.
Единственным исключением является CDP (Customer Data Platform)~---
административная панель клиента, которая развёртывается для каждого тенанта отдельно,
однако при обработке запросов обращается к общим мультитенантным микросервисам (\firef{fig:cdp-microservices}).


\begin{figure}[h]
  \centering
  \includegraphics[width=0.8\textwidth]{diagrams/img/ch1_cdp_microservices}
  \caption{Взаимодействие тенантных CDP и мультитенантных микросервисов}
  \label{fig:cdp-microservices}
\end{figure}

\subsection{Контуры развёртывания}\label{subsec:contours}

Для обеспечения изоляции сред и управления рисками при развёртывании
платформа разделена на несколько контуров.
На каждом из них развёртывается полный набор микросервисов компании,
что позволяет независимо тестировать и эксплуатировать платформу в разных окружениях.

\begin{itemize}
  \item \textbf{Alpha}~--- среда разработчиков.
    Предназначена для локальной отладки и интеграционного тестирования до попадания изменений на боевые контуры.
    Использует собственный набор криптографических ключей, изолированный от остальных контуров.
  \item \textbf{Beta}~--- контур предрелизного тестирования на ограниченной группе реальных пользователей.
    Позволяет выявить дефекты в условиях, приближённых к боевой эксплуатации, до масштабного развёртывания.
  \item \textbf{Gamma}~--- основное боевое окружение,
    обслуживающее подавляющее большинство клиентов и принимающее максимальную нагрузку.
    Именно на этом контуре обрабатывается свыше 2 миллионов запросов в минуту.
  \item \textbf{Sigma}~--- дополнительный боевой контур, функционально аналогичный Gamma.
    Создан для размещения новых клиентов и дальнейшего масштабирования платформы.
  \item \textbf{Omega}~--- полностью изолированный боевой контур,
    развёрнутый в облачной инфраструктуре AWS\@.
  \item \textbf{Infra}~--- внутренний инфраструктурный контур компании.
    Содержит инструменты администрирования проектами клиентов (CDP приложения)
    на всех вышеперечисленных контурах.
\end{itemize}

\subsection{Изолированность контуров}\label{subsec:contour-isolation}

Несмотря на архитектурное разделение,
изоляция между контурами умышленно нарушается в нескольких точках (\firef{fig:contour-interaction}).
Контур infra по своему назначению коммуницирует со всеми остальными контурами,
и наоборот~--- сервисы на боевых контурах отправляют запросы к infra для выполнения административных операций.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.6\textwidth]{diagrams/img/ch1_contour_interaction}
  \caption{Схема взаимодействия между контурами развёртывания}
  \label{fig:contour-interaction}
\end{figure}

Кроме того, часть микросервисов отсутствует на контуре Beta.
В таких случаях запросы с Beta перенаправляются на Gamma, образуя межконтурный fallback-маршрут.

Наиболее критичным с точки зрения безопасности является то,
что на всех контурах, кроме Alpha, используется \textbf{один и тот же закрытый RSA-ключ}
для подписи и верификации JWT-токенов.
Таким образом, компрометация ключа на любом из контуров автоматически ставит под угрозу все остальные.
Единый ключ порождает неявное межконтурное взаимодействие:
токен, выпущенный на одном контуре, валиден на любом другом,
и по самому токену невозможно определить, для какого контура он предназначен.
Это упрощает эксплуатацию,
однако при проектировании новой системы авторизации станет одной из ключевых сложностей~---
ротация ключа на одном контуре не должна нарушать работу остальных.

\subsection{Текущая схема JWT-авторизации}\label{subsec:jwt-scheme}

Для хранения секретов платформа использует HashiCorp Vault~\cite{HashiCorpVault}~---
систему централизованного управления секретами.
Все 120 микросервисов имеют доступ к закрытому RSA-ключу, хранящемуся в Vault.
Инструментарий для работы с авторизацией централизованно реализован
в библиотеке \texttt{Mindbox.Authentication},
которая предоставляет единый набор функций для генерации и проверки JWT-токенов
и используется всеми микросервисами платформы.
При этом централизованного контроля над выпуском токенов не существует~---
на практике сложились два разрозненных подхода к работе с JWT\@.

\begin{enumerate}
  \item \textbf{Статические токены в Vault.}
    Для межсервисного взаимодействия, не требующего динамических данных из рантайма,
    разработчик вручную генерирует JWT, подписывает его закрытым ключом и сохраняет в Vault как секрет.
    Чтобы избежать повторной ручной генерации,
    срок действия таких токенов устанавливается в 10 лет.
    В рантайме сервис просто считывает готовый токен из Vault
    и использует его для запросов (\firef{fig:static-jwt}).

    \begin{figure}[h]
      \centering
      \includegraphics[width=0.85\textwidth]{diagrams/img/ch1_static_jwt}
      \caption{Использование статического JWT-токена из Vault}
      \label{fig:static-jwt}
    \end{figure}

  \item \textbf{Динамическая генерация.}
    Когда в токен необходимо включить данные, известные только в момент запроса
    (например, идентификатор тенанта или пользователя),
    сервис самостоятельно получает закрытый ключ из Vault
    и подписывает JWT в рантайме.
    Этот подход применяется прежде всего для пользовательских токенов
    (\firef{fig:dynamic-jwt}).

    \begin{figure}[h]
      \centering
      \includegraphics[width=0.85\textwidth]{diagrams/img/ch1_dynamic_jwt}
      \caption{Динамическая генерация JWT в рантайме}
      \label{fig:dynamic-jwt}
    \end{figure}
\end{enumerate}

Однако граница между двумя подходами не контролируется:
любой микросервис имеет доступ к закрытому ключу
и может выпустить произвольный токен~--- как сервисный, так и пользовательский.
Схема авторизации не разделяет эти типы токенов: они имеют одинаковую структуру.

Помимо микросервисов, JWT-токены Mindbox используются сторонними системами:
платформой автоматизации Make, системой управления конфигурацией Ansible,
оркестратором развёртывания Octopus Deploy и CI/CD-системой GitLab.
Эти внешние потребители также хранят долгоживущие токены
и должны быть учтены при проектировании механизма ротации.

Описанная схема отличается простотой и удобством для разработчиков:
низкий порог входа и отсутствие централизованного сервиса авторизации
позволяли командам быстрыми темпами развивать продукт.

\subsection{Модель угроз текущей схемы авторизации}\label{subsec:threat-model}

Однако по мере роста платформы такая архитектура создаёт предпосылки для серьёзных инцидентов безопасности.
Чтобы перейти от интуитивного понимания рисков к обоснованным требованиям для новой системы,
необходим формальный анализ угроз.
Для этого была применена методология STRIDE~\cite{MicrosoftSTRIDE, OWASPThreatModeling},
разработанная в Microsoft и широко используемая для анализа безопасности программных систем.
STRIDE классифицирует угрозы по шести категориям,
каждая из которых соответствует нарушению определённого свойства безопасности (\taref{tab:stride-categories}).

    \hline
    Подмена идентичности (S) & Аутентичность & Выдача себя за другого пользователя или систему \\

    Отказ от авторства (R) & Неотказуемость & Невозможность доказать, кто совершил действие \\
    Раскрытие информации (I) & Конфиденциальность & Доступ к данным неавторизованным субъектом \\
    Отказ в обслуживании (D) & Доступность & Нарушение работоспособности системы \\

Корневой уязвимостью текущей архитектуры является доступность единого
закрытого RSA-ключа всем 120 микросервисам платформы.
Каждый сервис может самостоятельно генерировать JWT с произвольными claims,
а выпущенные токены принимаются на всех контурах.
Таким образом, компрометация любого из 120 сервисов равносильна
компрометации всей системы авторизации.

Применив категории STRIDE к описанной архитектуре,
были выявлены три угрозы, производные от компрометации ключа,
и четыре независимые архитектурные угрозы, усугубляющие последствия
и затрудняющие реагирование на инциденты.

\section{Технические требования к системе авторизации}\label{sec:requirements}

На основании проведённого анализа угроз и особенностей платформы Mindbox
сформулированы технические требования к новой системе авторизации.

\begin{enumerate}
  \item \textbf{Независимость от облачного провайдера.}
    Платформа Mindbox использует несколько облачных провайдеров одновременно.
    Система авторизации должна допускать локальное развёртывание (self-hosted)
    либо использование управляемого сервиса (managed)
    без привязки к конкретному облаку.
    Решения, доступные только в рамках одного провайдера, неприменимы.

  \item \textbf{Расширяемость процесса ротации.}
    При ротации ключей подписи платформа должна иметь возможность
    встроить дополнительные шаги в пайплайн ротации~---
    например, распространение обновлённых секретов и ключей
    по зависимым компонентам системы.
    Без такой расширяемости ротация не может быть выполнена корректно,
    поскольку платформа обладает рядом специфичных компонентов,
    требующих индивидуальной обработки при смене ключа.

  \item \textbf{Ротация как механизм отзыва.}
    Помимо плановой гигиенической смены ключей,
    механизм ротации используется для экстренного отзыва токенов
    при обнаружении утечки.
    Из этого следуют два подтребования:
    ротация должна выполняться достаточно быстро и полностью автоматизированно,
    а плановая ротация~--- частой,
    чтобы минимизировать окно, в течение которого скомпрометированный ключ остаётся активным.

  \item \textbf{Автоматическая ротация с ручным запуском.}
    Плановая ротация должна выполняться автоматически по расписанию.
    При этом должна быть предусмотрена возможность
    ручного запуска ротации в любой момент~---
    в частности, для реагирования на инциденты безопасности.

  \item \textbf{Бесшовность для потребителей.}
    Ротация ключей не должна приводить к отказу в обслуживании
    ни для одного из потребителей токенов.
    Токены, подписанные предыдущим ключом,
    должны оставаться валидными в течение grace-периода,
    а переход на новый ключ~--- происходить без вмешательства со стороны потребителей.

  \item \textbf{Минимальное влияние на задержку.}
    В текущей системе генерация и проверка токена выполняются локально,
    без сетевых вызовов, и вносят пренебрежимо малую задержку.
    Допустимый рост задержки на 95-м процентиле~---
    не более 60~мс на запрос.

  \item \textbf{Масштабируемость.}
    Система должна поддерживать горизонтальное и вертикальное масштабирование
    при двух характерных профилях нагрузки платформы:
    пакетной и транзакционной.
    Целевая пропускная способность~--- не менее 10\,000~RPS.

  \item \textbf{Наблюдаемость.}
    Система должна предоставлять средства мониторинга и оповещения:
    метрики выпуска и верификации токенов,
    статус ротации ключей,
    а также алерты при аномалиях~---
    например, при росте числа отклонённых токенов
    или при сбое процесса ротации.
\end{enumerate}

\section{Обзор технологий и стандартов межсервисной авторизации}\label{sec:tech-review}

На основании сформулированных требований
необходимо проанализировать существующие технологии и стандарты,
которые могут быть использованы при проектировании системы.
В данном разделе рассматриваются подходы,
каждый из которых адресует одно или несколько требований:
от транспортного шифрования через Service Mesh
до управления жизненным циклом токенов и ключей.

\subsection{Service Mesh и взаимная аутентификация на транспортном уровне}\label{subsec:service-mesh}

Первый подход, который необходимо рассмотреть,~---
устранение угроз на транспортном уровне через внедрение Service Mesh.
Service Mesh~--- это выделенный инфраструктурный слой,
расположенный между микросервисами и оркестратором~\cite{Koschel2021}.
Он перехватывает весь сетевой трафик микросервисов
через прокси-контейнеры (sidecar), развёрнутые рядом с каждым сервисом,
и реализует функции безопасности, маршрутизации и наблюдаемости
без модификации кода приложений~\cite{Li2019}.

Наиболее зрелой реализацией является Istio~\cite{Koschel2021},
архитектура которого представлена на \firef{fig:istio-arch}.
Компонент Citadel в составе Control Plane обеспечивает выпуск, распространение и ротацию
X.509-сертификатов для всех сервисов,
что позволяет использовать взаимную аутентификацию на транспортном уровне (mTLS)~\cite{PlatformV2025}.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.75\textwidth]{diagrams/img/istio-simplified-arch.png}
  \caption{Архитектура Service Mesh Istio: Data Plane (sidecar-прокси)
    и Control Plane (istiod)}
  \label{fig:istio-arch}
\end{figure}
Идентичность сервисов описывается в формате SPIFFE~\cite{SPIFFE}~---
стандарте, определяющем универсальный способ представления удостоверений
в распределённых системах.
При установлении mTLS-соединения (\firef{fig:mtls-handshake}) каждая из сторон
предъявляет сертификат, подписанный центром сертификации Service Mesh,
что одновременно обеспечивает аутентификацию обоих участников
и шифрование канала~\cite{Zimina2023}.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.85\textwidth]{diagrams/img/mtls.png}
  \caption{Последовательность взаимной аутентификации (mTLS)
    с участием центра сертификации}
  \label{fig:mtls-handshake}
\end{figure}

Однако внедрение Service Mesh сопряжено со значительными трудностями.
В работе~\cite{Li2019} показано, что Service Mesh существенно повышает
операционную сложность: каждый сервисный вызов проходит через дополнительный прокси,
а количество исполняемых экземпляров в кластере фактически удваивается.
Первое систематическое исследование безопасности Service Mesh~\cite{Hahn2020}
выявило критические недостатки:
ни один из рассмотренных инструментов (Consul, Istio, Linkerd)
не включает механизмы безопасности по умолчанию;
Consul не предоставляет возможности ротации или отзыва ключей шифрования;
а токены доступа во всех реализациях имеют бесконечный срок действия~(\taref{tab:mesh-defaults}).

В работе~\cite{Koschel2021} отмечается,
что Service Mesh применим преимущественно в высокоавтоматизированных средах,
поскольку именно в них его преимущества в части безопасности и наблюдаемости
могут быть реализованы в полной мере.
В случае Mindbox SRE-команда существует,
однако её ресурсы сосредоточены на задачах эксплуатации платформы,
а угрозы межсервисной авторизации требуют устранения немедленно~---
силами команды, ответственной за авторизацию.
Переход на Service Mesh предполагает одновременную миграцию
более 120~микросервисов, каждый из которых развёрнут на нескольких контурах,
что превращает внедрение в масштабный инфраструктурный проект,
несовместимый с требуемыми сроками.

Таким образом, Service Mesh с mTLS представляет собой целевое состояние
безопасности межсервисного взаимодействия,
однако не позволяет устранить выявленные угрозы в ближайшей перспективе.
Необходим подход, работающий на прикладном уровне~---
поверх существующей инфраструктуры и без её модификации.
Основным кандидатом для такого подхода является технология JWT.

\subsection{JSON Web Token}\label{subsec:jwt-overview}

JSON Web Token (JWT)~\cite{RFC7519}~--- открытый стандарт,
определяющий компактный и самодостаточный формат передачи утверждений (claims)
между двумя сторонами в виде JSON-объекта.
Токен состоит из трёх частей, разделённых символом <<.>>:
заголовка (header), полезной нагрузки (payload)
и подписи (signature)~\cite{Rahmatulloh2019},
как показано на \firef{fig:jwt-structure}.

\begin{figure}[h]
  \centering
  \includegraphics[width=0.75\textwidth]{diagrams/img/jwt-structure.png}
  \caption{Структура JSON Web Token: заголовок, полезная нагрузка и подпись}
  \label{fig:jwt-structure}
\end{figure}

Заголовок содержит идентификатор алгоритма подписи (\texttt{alg})
и тип токена (\texttt{typ}).
Полезная нагрузка включает набор утверждений~--- пар <<ключ-значение>>,
описывающих субъект, права доступа и метаданные.
Стандарт определяет зарезервированные утверждения:
\texttt{iss} (эмитент), \texttt{sub} (субъект), \texttt{aud} (аудитория),
\texttt{exp} (срок действия), \texttt{iat} (время выпуска) и другие~\cite{RFC7519}.
Подпись вычисляется над закодированными в Base64url заголовком и полезной нагрузкой
с использованием указанного алгоритма и секретного ключа,
обеспечивая целостность и подлинность токена.

Ключевым преимуществом JWT для микросервисной архитектуры
является отсутствие необходимости в централизованном хранилище сессий:
вся информация для авторизации запроса содержится в самом токене~\cite{Janoky2018}.
Это позволяет каждому сервису независимо проверять токен,
что обеспечивает горизонтальное масштабирование без единой точки отказа.
Систематический обзор литературы~\cite{Almeida2022}
подтверждает, что JWT является одним из трёх наиболее распространённых механизмов
аутентификации и авторизации в микросервисных системах,
наряду с OAuth~2.0 и API~Gateway.

Однако стандарт JWT не определяет механизма отзыва выпущенных токенов,
что является фундаментальной проблемой безопасности.
В работе~\cite{Janoky2018} классифицированы существующие подходы к отзыву
и построены математические модели их влияния на производительность.
Пусть $N$~--- число клиентов в системе,
$r$~--- число обращений к защищённым ресурсам в единицу времени,
$l$~--- стоимость проверки одного токена.
Тогда нагрузка на систему складывается из двух компонент:
нагрузки обращения $L_{\text{acc}}$ и нагрузки получения нового токена $L_{\text{tkn}}$.

\begin{itemize}
  \item \textbf{Короткоживущие токены.}
    Срок действия токена ограничивается коротким интервалом $T_{\text{lifetime}}$.
    По истечении срока клиент получает новый токен через refresh-механизм.
    Подход прост в реализации, однако создаёт постоянную нагрузку
    на сервис выдачи токенов:
    \begin{equation}\label{eq:short-lived}
      L_{\text{tkn}} = \frac{N}{T_{\text{lifetime}}}
    \end{equation}
    Кроме того, отзыв не мгновенный~--- в худшем случае
    скомпрометированный токен остаётся валидным на протяжении $T_{\text{lifetime}}$.

  \item \textbf{Чёрный список} (blacklist).
    Отозванные токены заносятся в централизованное хранилище,
    с которым сверяется каждый запрос.
    Обеспечивает мгновенный отзыв, но вводит обратно централизованное состояние~---
    именно то, чего JWT призван избегать.
    Обозначив стоимость проверки по чёрному списку как $b$,
    получим совокупную нагрузку на каждый запрос:
    \begin{equation}\label{eq:blacklist}
      L_{\text{acc}} = (l + b) \cdot r
    \end{equation}

  \item \textbf{Смена ключа подписи.}
    Автор рассматривает смену секрета как механизм отзыва,
    вызванного событиями выхода клиентов из системы.
    Поскольку секрет общий, каждое такое событие
    инвалидирует токены всех $N$ клиентов.
    Если $T_{\text{rvk}}(N)$~--- время до первого события отзыва
    среди $N$ клиентов, то:
    \begin{equation}\label{eq:secret-change}
      L_{\text{tkn}} = \frac{N}{T_{\text{rvk}}(N)}
    \end{equation}
    $T_{\text{rvk}}(N)$ убывает с ростом $N$,
    поэтому нагрузка растёт быстрее, чем линейно,
    и автор считает метод непригодным
    для высоконагруженных систем~\cite{Janoky2018}.
    Однако этот вывод относится к задаче реактивного отзыва токенов;
    в данной работе смена ключа решает другую задачу~---
    плановую ротацию по расписанию.
    Модель будет уточнена в следующих подразделах
    применительно к ротации с grace-периодом,
    где указанное ограничение снимается.
\end{itemize}

Помимо механизмов отзыва, важную роль играют превентивные меры.
RFC~8725~\cite{RFC8725} формализует лучшие практики использования JWT:
обязательную проверку алгоритма подписи,
запрет алгоритма \texttt{none},
валидацию утверждений \texttt{iss}, \texttt{aud} и \texttt{exp},
а также рекомендацию использовать короткий срок действия токенов.
В работе~\cite{Vencauskas2023} дополнительно показано,
что разделение внешней аутентификации и внутренней авторизации
с использованием отдельных токенов для каждого этапа
существенно снижает риски компрометации.

Выбор JWT в качестве основы межсервисной авторизации
порождает два практических вопроса:
как обеспечить регулярную смену ключей подписи без нарушения работы системы
и какой алгоритм подписи выбрать.
Эти вопросы рассматриваются в следующих двух подразделах.

\subsection{Бесшовная ротация криптографических ключей}\label{subsec:key-rotation}

Регулярная смена криптографических ключей подписи
является обязательным требованием стандартов информационной безопасности~\cite{GOST27001}.
Стандарт JWT не определяет механизма ротации,
поэтому его необходимо проектировать явно.

Экосистема JWT предусматривает для этого специальный стандарт~---
JSON Web Key (JWK)~\cite{RFC7517}, определяющий формат
представления криптографических ключей в виде JSON-объектов.
Набор таких ключей (JWK Set) публикуется через endpoint,
доступный потребителям токенов.
Каждый ключ содержит идентификатор \texttt{kid} (Key~ID),
который включается в заголовок JWT,
позволяя потребителю однозначно определить,
каким ключом был подписан конкретный токен.

Критическим условием корректности при любой схеме ротации является то,
что потребители токенов должны получать открытые ключи
исключительно из JWK Set endpoint, а не хранить их локально,~---
это обеспечивает автоматическое обнаружение нового ключа.
Конкретный алгоритм бесшовной ротации с grace-периодом,
разработанный в рамках данной работы,
описан в главе~\ref{ch:design}.

\subsection{Реализация ротации ключей в существующих системах}\label{subsec:idp-analysis}

Стандарт JWK реализуется основными промышленными системами
управления идентификацией (Identity Provider, IdP).
Для оценки возможности использования готового решения
проанализированы три распространённые системы
с точки зрения механизмов ротации ключей подписи.

Auth0~\cite{Auth0KeyRotation}~--- облачная платформа,
поддерживающая только ручную ротацию через Dashboard или Management API.
После ротации предыдущий ключ остаётся в JWKS
до явного отзыва администратором,
что обеспечивает неограниченный grace-период
с необходимостью ручного контроля за своевременным отзывом.
Платформа не предоставляет способа автоматически уведомить
внешнюю систему о факте ротации ключа.

Keycloak~\cite{KeycloakKeys}~--- решение с открытым исходным кодом,
допускающее локальное развёртывание.
Ротация выполняется вручную:
администратор создаёт новый key provider с более высоким приоритетом,
а предыдущий ключ переходит в пассивное состояние и остаётся в JWKS.
Keycloak позволяет подключать Java-плагины для реакции на события,
однако плагин срабатывает постфактум
и не может заблокировать или отложить ротацию.

Okta~\cite{OktaKeyRotation}~--- из рассматриваемых платформ
единственная, предоставляющая автоматическую ротацию, включённую по умолчанию.
Ротация выполняется приблизительно четыре раза в год,
однако расписание определяется Okta и может быть изменено без уведомления.
Механизм основан на трёх состояниях ключа: NEXT, ACTIVE и EXPIRED.
Новый ключ публикуется в JWKS за несколько недель до ротации,
а после переключения старый ключ удаляется из JWKS.
Бесшовность определяется тем, успел ли потребитель обновить кеш.
Событие ротации фиксируется в журнале с возможностью подписки
через HTTP-уведомление,
однако уведомление асинхронное и не может приостановить процесс.

Результаты сравнения обобщены в \taref{tab:idp-comparison}.
Ни одна из рассмотренных систем не предоставляет возможности
встроить пользовательскую логику \emph{до} или \emph{в процессе} ротации ключа.
Уведомления доступны только постфактум
и не гарантируют, что все потребители успели обнаружить новый ключ.
Платформа Mindbox обладает рядом особенностей,
которые необходимо учитывать при ротации ключей:
без их встраивания в процесс ротации
корректная работа системы авторизации не может быть обеспечена.
Данные ограничения готовых решений являются существенными.

\subsection{Алгоритмы подписи токенов}\label{subsec:signing-algorithms}

Паттерн ротации определяет \emph{как} менять ключи,
но не отвечает на вопрос, \emph{какой} алгоритм подписи использовать.
Стандарт JSON Web Algorithms (JWA)~\cite{RFC7518} определяет набор
криптографических алгоритмов, применимых для подписи JWT.
Они делятся на две категории:
симметричные, использующие общий секрет (семейство HMAC),
и асимметричные, основанные на паре открытого и закрытого ключей
(семейства RSA и ECDSA).

В контексте микросервисной авторизации асимметричные алгоритмы
имеют принципиальное преимущество:
для верификации токена достаточно открытого ключа,
а закрытый ключ хранится только у эмитента.
Это позволяет реализовать модель,
в которой единственный сервис авторизации подписывает токены закрытым ключом,
а все остальные микросервисы верифицируют их с помощью открытого ключа,
не имея возможности выпускать новые токены.

В работе~\cite{Rahmatulloh2019} проведено экспериментальное сравнение
производительности алгоритмов подписи JWT по трём параметрам:
времени генерации токена, размеру токена и скорости передачи.
Результаты (\taref{tab:signing-perf}) показали,
что HMAC превосходит остальные алгоритмы по всем метрикам,
однако неприменим в сценарии с разделением ролей эмитента и потребителя.
Среди асимметричных алгоритмов ECDSA генерирует токены
в 2,8~раза быстрее RSA и обеспечивает передачу в 1,9~раза быстрее
при равном размере подписи.

  \centering

    \hline
    \textbf{Параметр} & \textbf{HMAC} & \textbf{ECDSA} & \textbf{RSA} \\

    Время генерации токена, мкс & 21\,322 & 95\,845 & 268\,290 \\
    Размер токена, байт          & 109     & 164     & 164      \\

Помимо производительности, выбор алгоритма определяется
требованиями к криптостойкости.
Рекомендации NIST SP~800-57~\cite{NIST80057} устанавливают,
что для обеспечения уровня безопасности 128~бит
(минимально допустимого после 2030 года) необходим ключ RSA
длиной не менее 3072~бит, тогда как для ECDSA достаточно ключа в 256~бит.
Таким образом, ECDSA обеспечивает сопоставимую криптостойкость
при существенно меньших вычислительных затратах,
что является важным фактором для высоконагруженных систем.

Определившись с форматом токена и алгоритмом подписи,
необходимо решить, каким образом сервисы будут получать токены
для обращения друг к другу.

\subsection{Обмен токенами}\label{subsec:token-exchange}

Стандарт OAuth~2.0 Token Exchange~\cite{RFC8693} определяет протокол,
позволяющий клиенту обменять один токен безопасности на другой
у службы авторизации (Security Token Service, STS).
Протокол формализует два сценария,
ранее реализовывавшихся нестандартными способами:

\begin{itemize}
  \item \textbf{Делегирование} (delegation)~---
    сервис~A запрашивает токен для обращения к сервису~B от своего имени,
    действуя по поручению пользователя.
    Результирующий токен содержит утверждение \texttt{act},
    указывающее на сервис, выполняющий запрос.
  \item \textbf{Имперсонация} (impersonation)~---
    сервис~A получает токен, неотличимый от токена самого пользователя.
    Используется в сценариях,
    где целевой сервис не должен знать о промежуточном звене.
\end{itemize}

В работе~\cite{Matias2023} описана архитектура
с Security Token Service на входе микросервисной системы,
где внешний JWT преобразуется во внутренний токен
с ограниченными правами для конкретного сервиса.
Это подтверждает применимость паттерна Token Exchange
в промышленных микросервисных системах.

В контексте платформы Mindbox Token Exchange решает две задачи.
Во-первых, централизованный выпуск межсервисных токенов:
сервис предъявляет свой идентификационный токен службе авторизации
и получает целевой токен с ограниченным набором утверждений
(\texttt{aud}, \texttt{scope}),
предназначенный для конкретного потребителя.
Это устраняет угрозу~3 (повышение привилегий),
поскольку сервис не может самостоятельно сформировать произвольный токен.
Во-вторых, протокол обеспечивает безопасное межконтурное взаимодействие:
служба авторизации одного контура может выступать в роли STS,
выпускающего токены, доверяемые службой авторизации другого контура.
Это позволяет организовать федерацию между контурами~---
например, между продуктивным и тестовым окружениями~---
без передачи общих секретов.

Для того чтобы описанные механизмы~--- JWK Set endpoint для ротации ключей,
Token Exchange для получения токенов~---
были доступны потребителям единообразно и автоматически,
необходим стандартный протокол публикации метаданных сервера авторизации.

\subsection{OpenID Connect}\label{subsec:oidc}

OpenID Connect (OIDC)~\cite{OpenIDConnect}~--- протокол аутентификации,
построенный как слой идентификации поверх OAuth~2.0~\cite{RFC6749}.
Если OAuth~2.0 решает задачу авторизации~---
делегирования доступа к ресурсам без передачи учётных данных,~---
то OIDC дополняет его возможностью \emph{аутентификации},
то есть подтверждения личности пользователя или сервиса~\cite{Aldea2025}.

Центральным элементом OIDC является ID~Token~---
JWT, выпускаемый сервером авторизации и подтверждающий факт аутентификации.
В отличие от Access~Token, предназначенного для доступа к ресурсам,
ID~Token адресован клиентскому приложению
и содержит информацию об аутентифицированном субъекте.

Для проектируемой системы наибольший интерес представляет
механизм Discovery, определённый протоколом:
стандартизированный endpoint \texttt{.well-known/openid-configuration},
через который клиенты автоматически получают метаданные сервера авторизации~---
URL-адреса для выпуска токенов, JWK Set endpoint
и список поддерживаемых алгоритмов подписи.
Благодаря Discovery интеграция нового потребителя сводится к указанию
единственного URL сервера авторизации:
вся остальная конфигурация, включая адрес JWKS endpoint
для бесшовной ротации ключей, обнаруживается автоматически.
В обзоре литературы~\cite{Almeida2022} OIDC отмечен
как один из четырёх наиболее распространённых механизмов
обеспечения безопасности в микросервисных архитектурах.

Рассмотренные технологии~--- JWT, ротация ключей, Token Exchange, OIDC~---
формируют программный каркас системы авторизации.
Однако помимо кода самой системы необходимо управлять её конфигурацией:
перечнем сервисов-потребителей, их разрешениями и привязками к контурам.
Для этого применяется подход <<Инфраструктура как код>>.

\subsection{Инфраструктура как код}\label{subsec:iac}

Инфраструктура как код (Infrastructure as Code, IaC)~---
подход к управлению инфраструктурой,
при котором конфигурация описывается в виде декларативных файлов,
хранящихся в системе контроля версий~\cite{HashiCorpTerraform}.
Вместо ручного изменения конфигурации серверов и сервисов
администратор описывает желаемое состояние инфраструктуры,
а инструмент автоматически приводит реальное состояние в соответствие с описанным.

Одним из наиболее распространённых инструментов IaC является
Terraform~\cite{HashiCorpTerraform}~--- продукт компании HashiCorp
с открытым исходным кодом.
Terraform поддерживает декларативный язык конфигурации HCL
(HashiCorp Configuration Language),
строит граф зависимостей ресурсов
и применяет изменения параллельно там, где это допустимо.
Поддержка множества провайдеров (облачные платформы, базы данных,
системы управления секретами) делает Terraform универсальным инструментом
для описания гетерогенной инфраструктуры.

Преимущества IaC-подхода включают:
\begin{itemize}
  \item \textbf{воспроизводимость}~--- одна и та же конфигурация
    может быть применена на нескольких контурах,
    гарантируя идентичность среды;
  \item \textbf{версионирование}~--- история изменений инфраструктуры
    фиксируется в Git, что обеспечивает аудит и откат;
  \item \textbf{рецензирование}~--- изменения инфраструктуры проходят
    code review наравне с прикладным кодом;
  \item \textbf{автоматизация}~--- развёртывание и обновление инфраструктуры
    встраиваются в CI/CD-пайплайн.
\end{itemize}

В контексте данной работы IaC-подход применяется для управления
конфигурацией системы авторизации:
описания сервисов-потребителей, их разрешений и привязки к контурам.
Использование Terraform Provider позволяет командам разработки
самостоятельно регистрировать сервисы в системе авторизации
через декларативные конфигурационные файлы,
прошедшие процедуру рецензирования.
